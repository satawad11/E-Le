### โครงสร้างและเหตุผล

แยกสามตารางโดยตั้งใจ:

| ตาราง | หน้าที่ |
|---|---|
| `saraban_number_series` | ตั้งค่าชุดเลข — หน่วยงานใด ประเภทใด คำนำหน้าอะไร |
| `saraban_number_sequences` | **ตัวนับหนึ่งแถวต่อ (ชุดเลข, ปี พ.ศ.)** |
| `saraban_document_numbers` | เลขแต่ละเลขพร้อมสถานะและประวัติ |

**เหตุผลที่ต้องมีตารางตัวนับแยก:** SoT §9 ห้าม `SELECT MAX()+1` แบบไม่มี lock
การมีแถวตัวนับแถวเดียวทำให้ `lockForUpdate()` ล็อกได้ตรงจุด โดยไม่ต้องล็อกทั้งตารางเลข
— และเป็นรูปแบบเดียวกับ `LeaveDocumentNumberService` ที่ระบบเดิมใช้อยู่แล้ว (REUSE ของ pattern)

unique `(ชุดเลข, ปี, เลขที่)` เป็นด่านสุดท้ายของฐานข้อมูล ต่อให้ตรรกะพลาดก็ยังซ้ำไม่ได้

### การตัดสินใจเชิงออกแบบที่ควรบันทึก

**RELEASED ต่างจาก CANCELLED/VOID อย่างมีเหตุผล** — SoT §9 ระบุทั้งสามสถานะแยกกัน
แต่ไม่ได้บอกว่าต่างกันอย่างไร ผมตีความและบังคับไว้ในโค้ดดังนี้:

| สถานะ | ความหมาย | นำกลับมาใช้ได้ไหม |
|---|---|---|
| `RELEASED` | จองไว้แล้วคืน โดยยังไม่ได้ใช้ | **ได้** — ไม่งั้นทะเบียนจะมีเลขว่างโดยไม่จำเป็น |
| `CANCELLED` | ยกเลิกอย่างเป็นทางการก่อนออกเลข | ไม่ได้ตลอดไป |
| `VOID` | เพิกถอนหลังออกเลขไปแล้ว | ไม่ได้ตลอดไป · **เลขยังอยู่ในทะเบียนเป็นหลักฐาน** ไม่ถูกลบจนเกิดช่องว่างที่อธิบายไม่ได้ |

การหยิบเลขที่ RELEASED กลับมาใช้ ทำภายใต้ `lockForUpdate()` เช่นกัน เพื่อไม่ให้
สองคำขอหยิบเลขคืนใบเดียวกันไปพร้อมกัน

### เทสต์ concurrency จริง (ไม่ใช่การจำลอง)

SoT §9 บังคับ "concurrency-safe mandatory" ซึ่งเทสต์แบบลำดับเดียวพิสูจน์ไม่ได้
จึงรันของจริงบน MySQL:

```
10 process ขนานกัน × 20 เลขต่อ process = 200 การจอง
ผลลัพธ์: reserved=200  unique=200  min=1  max=200
```

**ได้เลข 1–200 ครบ ไม่ซ้ำแม้แต่เลขเดียว และไม่มีช่องว่าง** — ยืนยันว่าการล็อกแถว
ตัวนับทำงานจริงภายใต้การแย่งกันเขียน ไม่ใช่แค่ถูกต้องตอนเรียกทีละครั้ง

> ฐานข้อมูลชั่วคราวที่ใช้ทดสอบถูกลบทิ้งแล้ว และไม่ได้แตะฐานข้อมูล dev
