### 1. จุดตรวจสุขภาพ — แยกสองระดับเพราะผู้อ่านต่างกันโดยสิ้นเชิง

| | ใครเรียก | เห็นอะไร |
|---|---|---|
| `GET /api/health` | **uptime monitor ภายนอก** (ไม่มีบัญชี) | `{"status":"ok"}` เท่านั้น · 503 เมื่อระบบใช้ไม่ได้ |
| `GET /api/saraban/operations/health` | ผู้ดูแลที่มีสิทธิ์ | รายละเอียดครบ 8 ด้าน |

ถ้ารวมไว้ที่เดียว ต้องเลือกระหว่าง **"monitor เรียกไม่ได้"** กับ
**"เปิดเผยสถาปัตยกรรมภายในให้ทุกคน"** ซึ่งยอมรับไม่ได้ทั้งคู่ ·
มีเทสต์ตรึงว่าจุดสาธารณะคืนคีย์เดียวและไม่มีคำว่า `mysql`, `redis`, `driver`,
`latency`, `error` หลุดออกไป

**สองการตัดสินใจที่สำคัญ**

- **"ตรวจไม่ได้" = `down` ไม่ใช่ `ok`** — ตัวตรวจที่กลืนข้อผิดพลาดแล้วรายงานว่าปกติ
  อันตรายกว่าการไม่มีตัวตรวจเลย · แต่ละชิ้นห่อ try/catch **แยกกัน** ตัวตรวจจึงไม่ล้ม
  ทั้งตัวเพราะชิ้นเดียวพัง — ระบบที่มีปัญหาคือระบบที่ต้องใช้หน้านี้มากที่สุด
- **"ยังไม่เคยมีชีพจรเลย" = `degraded` ไม่ใช่ `ok`** — ระบบที่เพิ่งติดตั้ง กับระบบที่
  scheduler ไม่เคยทำงานเลย มีหน้าตาเหมือนกันทุกอย่าง · การรายงานว่าปกติจึงผิด

### 2. ⚠️ พบของจริง — การสำรองข้อมูลล้มเหลว **โดยไม่มีใครรู้**

ระหว่างพยายามสร้างไฟล์สำรองเพื่อทดสอบการกู้คืน ผมพบสองเรื่อง:

**(ก) `backup:run` ล้มเหลวในสภาพแวดล้อมนี้**

```
Backup failed because: mkdir(): File exists.
  at Spatie\TemporaryDirectory->empty()  (storage/app/backup-temp/temp)
```

ล้มทุกครั้งแม้ลบไดเรกทอรีทิ้งและรันด้วยผู้ใช้ `www-data` แล้ว · ผมแยกได้ว่า
**ไม่ใช่เรื่องสิทธิ์ไฟล์** (รันลำดับเดียวกันแยกออกมาสำเร็จ) แต่เกิดเฉพาะเมื่อรัน
ผ่าน `backup:run` เต็มขั้นตอนบน bind mount ของ Docker Desktop for Windows

**เพิ่มทางแก้ที่ตั้งค่าได้:** `BACKUP_TEMPORARY_DIRECTORY` — ย้ายไดเรกทอรีชั่วคราว
ออกจาก `storage/` ไปยังดิสก์ภายใน container เช่น `/tmp/backup-temp`
โดยไม่กระทบปลายทางที่เก็บไฟล์สำรองจริง

> **ผมยังหาสาเหตุที่แท้จริงไม่ได้ครบถ้วน และไม่ได้ยืนยันว่าทางแก้นี้ใช้ได้จริง**
> เพราะการทดสอบด้วย env ในสภาพแวดล้อมนี้ยังอ่านค่าไม่ติด · บันทึกเป็น
> **RISK-56** พร้อมสิ่งที่ตรวจไปแล้วทั้งหมด เพื่อให้ผู้ดูแลตรวจต่อได้ทันที
> **ผมไม่ได้อ้างว่าแก้แล้ว**

**(ข) ปัญหาที่ใหญ่กว่า — ความล้มเหลวนั้น "เงียบ"**

`config/backup.php` ส่งการแจ้งเตือนความล้มเหลวไปที่ **`your@example.com`**
ซึ่งเป็นค่าตัวอย่างของแพ็กเกจ · แปลว่า

> **การสำรองข้อมูลที่ล้มเหลวทุกคืน จะไม่มีใครรู้เลย จนถึงวันที่ต้องใช้ไฟล์สำรองจริง**

นี่คือความเสี่ยงที่ร้ายแรงกว่าตัวบั๊กเอง · ผมจึงเพิ่ม `RecordBackupOutcome`
ที่พาผลลัพธ์เข้าสู่ช่องทางที่ระบบนี้ใช้อยู่แล้ว — **REUSE ทั้งสองกลไก
ไม่สร้างช่องทางแจ้งเตือนใหม่**:

| เหตุการณ์ | ปลายทาง |
|---|---|
| สำรองล้มเหลว | คิวข้อผิดพลาดระดับ **`critical`** (INT-17) — มีเจ้าของ ติดตามได้ |
| ล้างไฟล์เก่าล้มเหลว | คิวระดับ `warning` — ยังไม่เสียข้อมูล แต่พื้นที่จะเต็ม |
| ไฟล์สำรองใช้ไม่ได้ | คิวระดับ `critical` |
| **สำรองสำเร็จ** | **ชีพจร** (INT-17) — ทำให้ "การสำรองที่เงียบหายไป" ถูกจับได้ด้วย |

ข้อสุดท้ายสำคัญไม่แพ้กัน: การสำรองที่ **หยุดทำงานไปเฉย ๆ** ไม่มีเหตุการณ์ล้มเหลว
ให้จับเลย · ชีพจรทำให้ความเงียบนั้นกลายเป็นรายการ `critical` ภายใน 48 ชั่วโมง
ผ่าน `operations:check-heartbeats` ของ INT-20

### 3. `backup:verify-restore` — ไฟล์สำรองที่ไม่เคยกู้ได้ ไม่ใช่ไฟล์สำรอง

> สำรองข้อมูลทุกคืนมาห้าปี แล้ววันที่ต้องใช้จริงจึงพบว่าไฟล์เสีย —
> เป็นความผิดพลาดที่พบบ่อยที่สุดในระบบราชการ

คำสั่งนี้ทำสิ่งที่คนมักไม่ทำ: **กู้คืนจริงลงฐานข้อมูลชั่วคราว** → ตรวจว่าตารางสำคัญ
(`users`, `permissions`, `menus`, `migrations`) **มีข้อมูลจริง ไม่ใช่แค่มีตาราง**
→ บันทึกเวลาที่ใช้ (RTO ที่วัดได้จริง) → ลบฐานชั่วคราวทิ้งเสมอแม้ล้มเหลว (`finally`)

**ไม่แตะฐานที่ใช้งานอยู่เลย** · ปฏิเสธที่จะทำงานบน production · และ
**ข้ามตัวเองบน SQLite พร้อมบอกเหตุผล** แทนที่จะทำแล้วรายงานผลลวง

### 4. หลักฐานการกู้คืนเชื่อมเข้าทะเบียน Compliance และ **หมดอายุได้**

หัวข้อ `restore` ใน Compliance Register (INT-20) เดิมเป็น `NO_EVIDENCE` เสมอ
ตอนนี้อ่านผลจริงจากชีพจรที่ `backup:verify-restore` บันทึกไว้:

| เงื่อนไข | สถานะ |
|---|---|
| ยังไม่เคยรันคำสั่ง | `NO_EVIDENCE` |
| รันสำเร็จภายใน 90 วัน | `PASS` |
| รันสำเร็จแต่เกิน 90 วัน | **`PARTIAL`** |

ข้อสุดท้ายคือหัวใจ: **ไฟล์สำรองที่กู้ได้เมื่อปีที่แล้ว ไม่ได้บอกอะไรเกี่ยวกับไฟล์
ของสัปดาห์นี้** · หลักฐานที่ไม่หมดอายุคือหลักฐานที่หลอกตัวเอง
· และยังคง **ไม่มีทางกรอกเองได้** ตามหลักการของ INT-20

### 5. โหมดอ่านอย่างเดียว — ต่างจาก `artisan down` โดยสิ้นเชิง

| | ผู้ใช้ทำอะไรได้ |
|---|---|
| `php artisan down` | **ไม่ได้เลย** |
| โหมดนี้ | **ค้นและเปิดดูหนังสือได้ · บันทึกไม่ได้** |

ใช้ตอนกู้คืนข้อมูล ย้ายฐานข้อมูล หรือระหว่างตรวจสอบเหตุการณ์ผิดปกติ —
ช่วงที่ต้องหยุดการเปลี่ยนแปลง **แต่งานราชการหยุดรอไม่ได้**

**สามการตัดสินใจ**

- **ตอบ 503 + `Retry-After` ไม่ใช่ 403** — ผู้เรียกต้องแยก "คุณไม่มีสิทธิ์" ออกจาก
  "ตอนนี้ไม่รับ ลองใหม่ทีหลัง" · ระบบภายนอกที่เห็น 403 จะเลิกลองใหม่ถาวร
- **ไม่ยกเว้นผู้ดูแลสูงสุด** — ถ้าผู้ดูแลยังเขียนได้ระหว่างกู้คืนข้อมูล
  ข้อมูลที่เพิ่งกู้มาจะถูกทับทันที · มีเทสต์ตรึง
- **ยกเว้นเฉพาะสามเส้นทาง**: ออกจากระบบ, เข้าสู่ระบบ, และ **ปุ่มปิดโหมดนี้เอง** —
  ไม่งั้นต้องแก้ฐานข้อมูลด้วยมือเพื่อออกจากโหมด

## UI-QA

**เช็คพอยต์นี้ไม่มีหน้าจอใหม่** — และเป็นการตัดสินใจ ไม่ใช่การละเลย:

- **สุขภาพระบบ** แสดงอยู่ในศูนย์เฝ้าระวัง (INT-17) แล้ว · การเพิ่มหน้าใหม่จะทำให้
  ผู้ดูแลต้องเปิดสองหน้าเพื่อดูเรื่องเดียวกัน
- **โหมดอ่านอย่างเดียว** เป็นธงในหน้าศูนย์เฝ้าระวังอยู่แล้ว (INT-17 แสดงธงทุกตัว
  จาก catalogue โดยอัตโนมัติ) — **ธงใหม่ปรากฏบนหน้าจอทันทีโดยไม่ต้องแก้ frontend**
  ซึ่งเป็นผลของการออกแบบที่ INT-17 วางไว้
- **หลักฐานการกู้คืน** แสดงในทะเบียนหลักฐาน (INT-20) แล้ว และเปลี่ยนจาก
  `NO_EVIDENCE` เป็น `PASS`/`PARTIAL` เองเมื่อมีหลักฐานจริง

**ข้อความที่ผู้ใช้เห็นเมื่อระบบอยู่ในโหมดอ่านอย่างเดียว** เขียนให้บอกทั้งสิ่งที่ยังทำได้
และสิ่งที่ทำไม่ได้ พร้อมบอกว่าเป็นการชั่วคราว — ไม่ใช่ข้อความ error ที่ทำให้ผู้ใช้
คิดว่าตนทำผิดหรือระบบเสีย

**ข้อจำกัดเดิม:** ไม่ได้ทำ visual QA ผ่านเบราว์เซอร์จริง

## EVIDENCE

- ผลรัน `php artisan test` (1,029 ผ่าน), `pint --test`, gates ฝั่งหน้าเว็บ
- **ข้อความ error จริงของ `backup:run`** ที่ยกมาในหัวข้อ DONE ข้อ 2 —

- เทสต์จุดตรวจสาธารณะ **ค้นหาคำที่ห้ามรั่วในผลลัพธ์จริง** ไม่ใช่ตรวจแค่โครงสร้าง

- เทสต์โหมดอ่านอย่างเดียวยิงคำขอจริงทั้งอ่านและเขียนแล้วเทียบ status code

**หลักฐานที่ผมยัง "ไม่มี" และไม่อ้างว่ามี:**

| สิ่งที่ยังไม่มีหลักฐาน | เหตุผล |
|---|---|
| การกู้คืนสำเร็จจริงจากไฟล์สำรองจริง | สร้างไฟล์สำรองในสภาพแวดล้อมนี้ไม่ได้ (RISK-56) |
| RTO ที่วัดจากการกู้คืนจริง | ตามข้อบน |

ทะเบียน Compliance จึงยังรายงาน `restore` เป็น **`NO_EVIDENCE`** ซึ่ง**ถูกต้อง**
— และเป็นการพิสูจน์ว่ากลไกที่ออกแบบไว้ที่ INT-20 ทำงานตามเจตนา: มันไม่ยอม
รายงาน PASS ให้สิ่งที่ยังไม่ได้เกิดขึ้นจริง
