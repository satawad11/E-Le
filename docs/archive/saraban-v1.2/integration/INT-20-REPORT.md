### 1. IDOR — รูปแบบที่อันตรายที่สุดคือ "มีสิทธิ์ครบแต่อยู่นอกขอบเขต"

เทสต์สร้างผู้ใช้ที่ถือสิทธิ์ **ครบ 5 ตัว** (`document.view`, `document.update`,
`incoming.stamp`, `endorse.create`, `distribution.track`) แต่อยู่คนละหน่วยงาน
แล้วยิงเข้า 6 endpoint ที่รับ id ของหนังสือ

ด่าน `ability:` ผ่านหมดทุกข้อ — **สิ่งที่ต้องหยุดเขาคือ `authorize()` รายชิ้น**
ถ้า endpoint ใดลืมเรียก มันจะหลุดตรงนี้ทันที

ยอมรับทั้ง 403 และ 404 เพราะบาง endpoint ตอบ 404 โดยตั้งใจเพื่อไม่ยืนยันว่า
ทรัพยากรมีอยู่จริง (INT-13, INT-18) · สิ่งที่ต้องไม่เกิดคือ 2xx

### 2. การตรวจชนิดไฟล์ — เทสต์เดิมอาจวัด "ของปลอม" ไม่ใช่กติกา

ตอนเขียนเทสต์นี้ครั้งแรกผมใช้ `UploadedFile::fake()->createWithContent('x.pdf', '<?php ...')`
แล้ว**เทสต์ล้มเหลวเพราะระบบรับไฟล์นั้น** — ดูเหมือนพบช่องโหว่

ตรวจสอบแล้วพบว่า **ไม่ใช่ช่องโหว่ แต่เป็นข้อจำกัดของ `UploadedFile::fake()`**
ซึ่งประกาศ MIME ตามนามสกุลที่ตั้งให้ ทำให้กติกา `mimetypes:` ได้ค่าปลอมไปตรวจ

แก้โดยเขียนไฟล์จริงลงดิสก์แล้วส่งผ่าน `new UploadedFile($path, 'ห.pdf', null, null, true)`
ซึ่งทำให้ `mimetypes:` เรียก finfo อ่านเนื้อไฟล์จริง · **ผลคือระบบปฏิเสธถูกต้องอยู่แล้ว**
และเพิ่มเทสต์คู่ที่ยืนยันว่า PDF จริงยังผ่าน (ไม่งั้นเทสต์แรกอาจผ่านด้วยเหตุผลที่ผิด)

> บทเรียนที่บันทึกไว้: **เทสต์ความปลอดภัยที่ใช้ของปลอมอาจให้ความมั่นใจที่ผิด**
> ทั้งสองทาง — ทั้งบอกว่าปลอดภัยทั้งที่ไม่ และบอกว่าไม่ปลอดภัยทั้งที่ปลอดภัย

### 3. RISK-22 ปิดแล้ว — หลักฐานที่รันซ้ำได้ ไม่ใช่หลักฐานที่หมดอายุ

INT-06 เคยพิสูจน์การออกเลขแบบทนการแย่งกันด้วยมือ (10 process × 20 ครั้ง)
แต่ **การพิสูจน์ครั้งเดียวแล้วไม่มีใครรันอีกคือหลักฐานที่หมดอายุ**

ชุดทดสอบปกติพิสูจน์เรื่องนี้ไม่ได้ เพราะรันบน SQLite `:memory:` ซึ่งเป็นฐานเดียว
ต่อหนึ่ง process และไม่มี row-level lock จริง — เทสต์ที่ผ่านบนนั้นไม่ได้บอกอะไรเลย
เกี่ยวกับ MySQL ซึ่งเป็นฐานที่ใช้จริง

จึงทำเป็นคำสั่งที่ **เปิด process จริงหลายตัวพร้อมกัน** (`proc_open`) ไม่ใช่วนใน
process เดียว — การวนใน process เดียวไม่มีการแย่งกันเลย ต่อให้เขียนโค้ดผิดก็ผ่าน

**ผลรันจริงบน MySQL 8 ในรอบนี้:**

```
$ php artisan saraban:concurrency-check --workers=8 --per-worker=15
+-----------+-----+
| ขอทั้งหมด  | 120 |
| ได้รับจริง  | 120 |
| ไม่ซ้ำกัน   | 120 |
| เลขต่ำสุด  | 1   |
| เลขสูงสุด  | 120 |
+-----------+-----+
ผ่าน — 8 process ขอพร้อมกันได้เลขไม่ซ้ำครบ 120 เลข
```

เกณฑ์ผ่านสามข้อพร้อมกัน เพราะขาดข้อใดข้อหนึ่งแปลว่ามีปัญหาคนละแบบ:
**ได้ครบ** (ไม่มีคำขอล้มเงียบ) · **ไม่ซ้ำ** (อันตรายที่สุด) · **ไม่มีช่องว่าง**
(ไม่มีเลขหายโดยไม่มีใครถือ)

> รันบนฐานชั่วคราว `eleave_conc` แล้วลบทิ้ง — ไม่แตะฐานพัฒนา
> คำสั่งปฏิเสธที่จะทำงานบน production และข้ามตัวเองบน SQLite พร้อมบอกเหตุผล

### 4. RISK-46 ปิดแล้ว — จาก "มองเห็นได้ถ้ามีคนดู" เป็น "งานที่มีเจ้าของ"

INT-17 ทำให้ความเงียบของงานตามเวลามองเห็นได้บนหน้าจอ — **แต่ไม่มีใครเปิดหน้าจอนั้น
จนกว่าจะมีคนโทรมาถามว่าทำไมไม่ได้รับการแจ้งเตือน**

`operations:check-heartbeats` (ทุก 15 นาที) ยกงานที่เงียบเกินกำหนดเข้าคิว
ข้อผิดพลาดระดับ `critical` ซึ่งมีเจ้าของ มีสถานะ และไหลต่อไปยังศูนย์แจ้งเตือนได้

> **ปัญหาไก่กับไข่ที่ต้องยอมรับตรง ๆ:** ตัวมันเองก็เป็นงานตามเวลา ถ้า `schedule:run`
> ตายทั้งหมด คำสั่งนี้ก็ไม่ทำงานเช่นกัน · **การเฝ้าระวังชั้นสุดท้ายต้องมาจาก
> ภายนอกระบบ** — uptime monitor ที่เรียก `/api/ping` ซึ่งอยู่นอกขอบเขตของโค้ดนี้
> · ระบุไว้ทั้งในคอมเมนต์ของคำสั่งและที่นี่ ดีกว่าปล่อยให้เข้าใจว่าครอบคลุมแล้ว (RISK-54)

### 5. RISK-52 ปิดแล้ว — ทะเบียนหลักฐานที่โกหกไม่ได้

SoT §23 บังคับว่า **"ห้าม claim PASS โดยไม่มี evidence จริง"**

ผมบังคับข้อนี้ **ด้วยการออกแบบ ไม่ใช่ด้วยความไว้ใจ**:

- **ไม่มีตารางเก็บสถานะ** — ไม่มีที่ให้ใครเขียน
- **ไม่มี endpoint ที่เปลี่ยนสถานะ** — มีเทสต์กวาด route ยืนยันว่าไม่มี
  POST/PUT/PATCH/DELETE ใดชี้มาที่ compliance
- **ทุกสถานะคำนวณสด** จากการตรวจจริง ณ เวลาที่เรียก
- **หัวข้อที่ตรวจอัตโนมัติไม่ได้คืน `NO_EVIDENCE` เสมอ** และไม่มีทางกลายเป็น PASS

**15 หัวข้อ กับวิธีตรวจจริงของแต่ละข้อ:**

| หัวข้อ | ตรวจอย่างไร |
|---|---|
| permission | นับชื่อสิทธิ์ในฐานเทียบกับ manifest |
| workflow | นับ `workflow_versions` ที่ published |
| authority | นับ `permission_scopes` + `org_unit_managers` |
| **audit** | **ไล่เทียบ hash ทุกแถวใน `audit_logs` จริง** |
| backup | นับไฟล์ .zip ใน disk ปลายทางจริง |
| restore / DR / UAT / accessibility | **`NO_EVIDENCE` เสมอ** — ต้องมีคนลงมือ |
| security | อ่าน config จริง 4 ข้อ + ตรวจว่ามีหลักฐานการลงนาม |
| migration | นับแถวในตาราง `migrations` |
| provider | นับผลส่งจริงใน `notification_deliveries` |
| contracts | นับ webhook endpoints (`N/A` ถ้าไม่มี — ไม่ใช่ FAIL) |
| **incidents** | **นับรายการค้างในคิว — มีค้าง = FAIL** |
| retention | นับกำหนดการเก็บรักษาและการอายัด |

เทสต์ยืนยันว่า **audit chain ที่ถูกแก้รายงาน FAIL** (แก้ `previous_hash` ตรงฐาน
แล้วเรียกซ้ำ) และ **ข้อผิดพลาดที่ค้างทำให้ incidents เป็น FAIL** — ไม่ใช่แค่ตรวจว่า
มีตาราง

### 6. สมรรถนะ — เพิ่มดัชนีตามการใช้จริง ไม่ใช่เผื่อไว้ก่อน

ดัชนีทุกตัวมีราคาตอนเขียน · ดัชนีที่ไม่มีใครใช้คือค่าใช้จ่ายล้วน ๆ
เพิ่มเฉพาะสามตัวที่มี query จริงเรียกใช้:

| ดัชนี | query ที่เรียกใช้ |
|---|---|
| `saraban_documents.created_by` | `DocumentController::index()` ทำ `whereIn(...) orWhere(created_by)` — ครึ่งหลังยังสแกนทั้งตาราง |
| `saraban_documents (status, finalized_at)` | รายงานทะเบียนและคิวการทำลาย (INT-19) |
| `saraban_distribution_recipients (recipient_id, acknowledged_at)` | การนับ "ยังไม่รับทราบ" ในกล่องหนังสือเข้า |

เทสต์ N+1 นับ query จริงด้วย `DB::listen()` โดยใช้ **เกณฑ์หลวม ๆ โดยตั้งใจ** —
สิ่งที่ต้องจับคือ "จำนวน query โตตามจำนวนแถว" ไม่ใช่ตัวเลขที่แน่นอน ซึ่งจะพัง
ทุกครั้งที่มีคนเพิ่ม middleware
