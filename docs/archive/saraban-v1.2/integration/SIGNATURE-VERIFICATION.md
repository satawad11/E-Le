# SIGNATURE VERIFICATION — คู่มือความสามารถ

**Source of Truth:** `SARABAN-V1.2-EXISTING-SYSTEM-MODULE-MASTER.md` §8, §12, §14, §18, §24, §26
**ฉบับ:** 2026-09-05

---

## สิ่งที่ระบบนี้ทำ และไม่ทำ

> **ระบบนี้ทำ Electronic Signature ไม่ใช่ Digital Signature**

| | Electronic Signature (สิ่งที่ทำได้จริง) | Digital Signature (ยังไม่ได้ทำ) |
|---|---|---|
| ผูกกับตัวตน | ✅ ผ่านการยืนยันตัวตนซ้ำ + โทเคนที่บันทึกไว้ | ✅ ผ่านกุญแจส่วนตัว |
| ตรวจการแก้ไขไฟล์ | ✅ แฮช SHA-256 ของฉบับที่ลงนาม | ✅ ลายเซ็นเชิงรหัสวิทยา |
| พิสูจน์ต่อบุคคลที่สาม | ❌ ต้องเชื่อถือระบบนี้ | ✅ พิสูจน์ได้โดยไม่ต้องเชื่อระบบ |
| ใบรับรอง | ❌ ไม่มี | ✅ มี |

**โครงสร้างพร้อมรับใบรับรองแล้ว** (คอลัมน์ ตรรกะการตรวจ และรายชื่อที่เชื่อถือ)
แต่ **จะไม่มีที่ใดในระบบอ้างว่าเป็นลายเซ็นดิจิทัลจนกว่าจะมีใบรับรองจริง** —
การประกาศ `signature_type = digital` โดยไม่มีข้อมูลใบรับรอง ระบบจะรายงานว่า
**ไม่ผ่านทันที** เพราะเป็นการอ้างสิ่งที่พิสูจน์ไม่ได้

## สถานะการตรวจสอบ

เรียงจากเบาไปหนัก · **สถานะรวมคือข้อที่ร้ายแรงที่สุด ไม่ใช่การนับคะแนน**

| สถานะ | หมายความว่า | ใช้อ้างอิงได้ |
|---|---|---|
| `VALID` | ผ่านทุกข้อ | ✅ |
| `UNVERIFIED` | ยังไม่มีลายเซ็นให้ตรวจ | ❌ (ยังไม่ใช่ความล้มเหลว) |
| `VALID_WITH_WARNINGS` | ผ่าน แต่มีข้อสังเกต เช่น อำนาจของผู้ลงนามสิ้นสุดแล้ววันนี้ | ✅ |
| `REVOCATION_PENDING` | มีคำขอเพิกถอนรอการตัดสิน | ❌ |
| `TIMESTAMP_INVALID` | เวลาที่ประทับเชื่อถือไม่ได้ | ❌ |
| `CERTIFICATE_UNTRUSTED` | ผู้ออกใบรับรองไม่อยู่ในรายชื่อที่ประกาศไว้ | ❌ |
| `CERTIFICATE_EXPIRED` | ใบรับรองหมดอายุก่อนการลงนาม | ❌ |
| `CERTIFICATE_REVOKED` | ใบรับรองถูกเพิกถอนก่อนการลงนาม | ❌ |
| `SIGNATURE_ORDER_INVALID` | ลงนามผิดลำดับที่กำหนดไว้ | ❌ |
| `AUTHORITY_INVALID` | ไม่มีบันทึกอำนาจลงนาม หรือไม่พบผู้ลงนามแล้ว | ❌ |
| `SIGNER_MISMATCH` | ผู้สร้างฉบับที่ลงนามไม่ใช่ผู้ลงนามที่ระบุ | ❌ |
| `INVALID` | การผูกเวอร์ชันเสียหาย ไฟล์หาย หรืออ้าง digital โดยไม่มีใบรับรอง | ❌ |
| `DOCUMENT_MODIFIED_AFTER_SIGNING` | ไฟล์ถูกแก้หลังการลงนาม | ❌ |
| `REVOKED` | ถูกเพิกถอนแล้ว — **ชนะผลตรวจทางเทคนิคทุกข้อ** | ❌ |

## การตรวจแต่ละข้อ

ตรวจ **ฝั่ง server เท่านั้น** และ **คำนวณสดทุกครั้ง ไม่เก็บผลลงฐานข้อมูล** —
ผลที่เก็บได้คือผลที่แก้ได้ และผลของเมื่อวานตอบคำถามของวันนี้ไม่ได้

| ข้อตรวจ | ถามอะไร |
|---|---|
| `version_binding` | หลักฐาน ↔ เวอร์ชัน ↔ หนังสือ ผูกกันครบสามทาง และแฮชตรงกันไหม |
| `integrity` | ไฟล์บนดิสก์ยังตรงกับแฮชที่บันทึกตอนลงนามไหม |
| `signer_identity` | ผู้สร้างฉบับที่ลงนาม เป็นผู้ลงนามคนเดียวกันไหม · มีบันทึกยืนยันตัวตนซ้ำไหม |
| `authority` | มีบันทึกอำนาจ ณ วันลงนามไหม · อำนาจนั้นยังอยู่ในปัจจุบันไหม |
| `signing_order` | ลำดับเวลาจริงตรงกับลำดับที่กำหนดไว้ไหม |
| `certificate` | *(เฉพาะเมื่อมีใบรับรอง)* อายุ การเพิกถอน และผู้ออกที่เชื่อถือ |
| `timestamp` | *(เฉพาะเมื่อมี TSA)* เวลาสอดคล้องกับการลงนาม และผู้ให้บริการที่เชื่อถือ |
| `metadata_seal` | ข้อมูลทะเบียนถูกแก้หลังออกหนังสือไหม |
| `document_status` | หนังสือถูกยกเลิกแล้วหรือไม่ |

**ลำดับสำคัญ:** ตรวจ `integrity` **เฉพาะเมื่อ `version_binding` ผ่าน** — จะบอกว่า
"ไฟล์ถูกแก้หลังลงนาม" ได้ ต้องรู้ก่อนว่าไฟล์ไหนคือไฟล์ที่ลงนาม

## อำนาจลงนาม — ข้อจำกัดที่ต้องรู้

`authority_snapshot` ที่บันทึกไว้ตอนลงนาม **คือหลักฐานของอำนาจ ณ วันนั้น
ไม่ใช่สิ่งที่คำนวณซ้ำได้**

เหตุผล: สิทธิ์ในระบบ (spatie) **ไม่มีประวัติย้อนหลัง** · ถามวันนี้ว่า "เมื่อสองปีก่อน
คนนี้มีสิทธิ์ไหม" จะได้คำตอบของวันนี้เสมอ · ถ้าใช้ผลนั้นตัดสิน หนังสือที่ลงนาม
ถูกต้องจะกลายเป็นไม่ถูกต้องทันทีที่ผู้ลงนามเกษียณ ซึ่งเป็นคำตอบที่ผิด

snapshot เขียนโดยระบบเองด้วย `AuthorityResolver` ตัวเดียวกัน ณ วินาทีที่ลงนาม
และหลักฐานแก้ไม่ได้ที่ระดับโมเดล จึงเป็นบันทึกที่เชื่อถือได้เท่าที่ระบบนี้ทำได้

> **การพิสูจน์ที่แน่นกว่านี้ต้องมีประวัติสิทธิ์แบบมีช่วงเวลา** ซึ่งเป็นการเปลี่ยน
> แกนกลางของระบบ ไม่ใช่ขอบเขตของงานนี้ — บันทึกไว้เป็นข้อจำกัดที่รู้ตัว

## วงจรการเพิกถอน

```
ยื่นคำขอ (มีเหตุผล ≥ 10 ตัวอักษร + step-up)
        ↓
   รอการตัดสิน  →  REVOCATION_PENDING (หน้าสาธารณะบอกว่าใช้อ้างอิงไม่ได้)
        ↓
 ┌──────┴──────┐
อนุมัติ        ปฏิเสธ (ต้องมีเหตุผล)
 ↓              ↓
REVOKED      หนังสือใช้ได้ตามเดิม
หนังสือ =    คำขอยังอยู่ในทะเบียน
cancelled
```

**สามข้อที่บังคับเสมอ**

1. **เหตุผลบังคับ** — การเพิกถอนที่ไม่มีเหตุผลคือการลบร่องรอย
2. **ผู้ขอ ≠ ผู้ตัดสิน** (SoT §26) — บังคับที่ server ไม่ใช่แค่ซ่อนปุ่ม
3. **ยืนยันตัวตนซ้ำทั้งตอนขอและตอนตัดสิน** (SoT §24) — ตรวจทั้งที่ route
   (`step_up` → 423) และในบริการอีกชั้น

**ไม่ลบอะไรเลย** — การอนุมัติเปลี่ยนสถานะเป็น `cancelled` เท่านั้น · ไฟล์
หลักฐานการลงนาม เลขหนังสือ และทะเบียนยังอยู่ครบ เพราะผู้ที่ถือกระดาษต้อง
สแกน QR แล้วเห็นว่าฉบับนั้นถูกเพิกถอนแล้ว ซึ่งเป็นไปไม่ได้ถ้าลบข้อมูลทิ้ง

**คำขอที่ถูกปฏิเสธยังอยู่ในทะเบียน** — ต้องตอบได้ว่าเคยมีคนขอเพิกถอนหนังสือ
ฉบับนี้ด้วยเหตุผลใด และใครเป็นผู้ปฏิเสธ

## API

| Method | Path | สิทธิ์ | คืนอะไร |
|---|---|---|---|
| GET | `/api/saraban/documents/{document}/verification` | `saraban.document.view` + policy รายฉบับ | ผลตรวจฉบับเต็ม พร้อมเหตุผลรายข้อ |
| GET | `/api/saraban/documents/{document}/verification/report` | เหมือนกัน | ผลตรวจ + ชุดหลักฐาน + ประวัติคำขอเพิกถอน |
| POST | `/api/saraban/documents/{document}/revocations` | `saraban.signature.revoke` + `step_up` | ยื่นคำขอ |
| GET | `/api/saraban/revocations/pending` | `saraban.signature.revoke_approve` | คิวคำขอ (กรองด้วยขอบเขตของผู้เรียก) |
| POST | `/api/saraban/revocations/{revocation}/decision` | `saraban.signature.revoke_approve` + `step_up` | อนุมัติหรือปฏิเสธ |
| GET | `/api/saraban/verify/{hash}` | **สาธารณะ** | สถานะอย่างย่อเท่านั้น |

ทุกเส้นทางมีคู่ `api/v1/saraban/...` โดยอัตโนมัติตามที่ INT-15 วางไว้

### หน้าตรวจสอบสาธารณะ — สิ่งที่ **ไม่** คืน

คืนเฉพาะ `verification_status` และ `is_valid` · **ไม่คืน** เหตุผลรายข้อ ชุดหลักฐาน
จำนวนลายเซ็น สถานะคำขอเพิกถอนโดยละเอียด IP user agent path ของไฟล์ หรือแฮช

> คนทั่วไปที่ถือกระดาษต้องรู้แค่ว่าเอกสารในมือใช้อ้างอิงได้ไหม · รายละเอียดว่า
> อำนาจของใครหมดอายุหรือไฟล์ถูกแก้ที่จุดใด เป็นข้อมูลภายในที่บอกโครงสร้าง
> องค์กรและช่องโหว่ให้ผู้ไม่หวังดี

## สิทธิ์และค่าตั้งต้น

| สิทธิ์ | ค่าตั้งต้น | เหตุผล |
|---|---|---|
| `saraban.signature.revoke` | เจ้าหน้าที่ธุรการ | เป็นผู้พบความผิดพลาดของหนังสือที่ออกไปแล้ว |
| `saraban.signature.revoke_approve` | ผู้อำนวยการ | เป็นผู้ลงนาม จึงเป็นผู้เพิกถอน |

การจับคู่แบบนี้ทำให้ **แยกหน้าที่ได้จริงตั้งแต่วันแรก** โดยไม่ต้องรอผู้ดูแลมาตั้งค่า ·
ปรับได้จากหน้าจอจัดการสิทธิ์ตามโครงสร้างจริงของหน่วยงาน

การตรวจสอบใช้สิทธิ์เดียวกับการเปิดดูหนังสือ — ผู้ที่เปิดหนังสือได้ต้องตรวจสอบ
ความน่าเชื่อถือของมันได้ด้วย · การแยกสิทธิ์เพิ่มจะทำให้คนส่วนใหญ่เห็นลายเซ็น
แต่ไม่รู้ว่ามันยังใช้ได้ไหม ซึ่งแย่กว่าไม่แสดงเลย

## นโยบายความน่าเชื่อถือ (ศูนย์นโยบาย · SoT §18)

คีย์ `signature` มีสองรายการ:

```
trusted_certificate_issuers   → []   (ยังไม่ประกาศ)
trusted_timestamp_authorities → []   (ยังไม่ประกาศ)
```

**รายชื่อว่าง = ยังไม่ได้ประกาศว่าเชื่อถือใคร จึงไม่ตัดสินว่าไม่น่าเชื่อถือ** —
ต่างจาก "ประกาศแล้วและรายนี้ไม่อยู่ในรายการ" ซึ่งจะได้ `CERTIFICATE_UNTRUSTED`

เมื่อเริ่มใช้ลายเซ็นดิจิทัลจริง ให้เติมรายชื่อจากหน้าศูนย์นโยบาย — **ไม่ต้องแก้โค้ด**
และมีประวัติว่าเปลี่ยนเมื่อใดโดยใคร พร้อมย้อนกลับได้

## หน้าจอ

ทั้งหมดอยู่ใน **ส่วนประกอบเดิมของระบบ** ไม่มีหน้าจอใหม่:

- `DocumentTools.vue` — ผลตรวจพร้อมเหตุผลรายข้อ · ชุดหลักฐานฉบับเต็ม ·
  ปุ่มขอเพิกถอน · ปุ่มอนุมัติ/ปฏิเสธ (เฉพาะผู้มีอำนาจและเมื่อมีคำขอค้างอยู่)
- `OperationsTools.vue` — คิวคำขอเพิกถอนที่รอการตัดสิน
- `VerifyDocumentView.vue` — หน้าสาธารณะ (ใช้ `is_valid` ที่เข้มขึ้นแล้ว)

**หน้าจอไม่คำนวณสถานะเอง** — แปลงรหัสที่ server ส่งมาเป็นคำภาษาไทยเท่านั้น ·
รหัสที่ไม่รู้จักแสดงว่า "ตรวจสอบไม่ได้" ไม่ใช่ "ผ่าน" เพราะการเดาว่าผ่านคือความเสี่ยง
