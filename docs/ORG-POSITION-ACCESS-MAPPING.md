# ตารางจับคู่ ตำแหน่ง → ประเภทบุคลากร → บทบาท → หน่วยงาน/ขอบเขต

> **สถานะ: ร่างเพื่อพิจารณา (2026-10-16)** — ยังไม่ได้แก้ข้อมูลจริง ไม่มี migration และไม่มีการเปลี่ยนโค้ด
> ทุกอย่างในเอกสารนี้ทำได้ด้วย **การตั้งค่าข้อมูลผ่านหน้าจอ** ยกเว้นข้อที่ระบุไว้ในหัวข้อ 7
> ต้องให้เจ้าของระบบ/งานบุคลากรยืนยันคำถามในหัวข้อ 6 ก่อนลงมือ (ตอบแล้ว Q1, Q2 — ดู 6.1)

## 1. หลักคิด: แยก 4 เรื่องออกจากกัน

คำขอของผู้ใช้ ("ผู้บริหาร / ครู / เจ้าหน้าที่" และตำแหน่งย่อย) ปนกันอยู่ 4 เรื่อง ระบบเก็บแต่ละเรื่องไว้คนละที่ และ **สิทธิ์ต้องไม่ผูกกับชื่อตำแหน่ง** (PROJECT_RULES: ห้าม hard-code ประเภทบุคลากร, ห้ามใช้ชื่อ role เป็น business logic)

| ชั้น | ตอบคำถาม | เก็บที่ | ใช้ทำอะไร |
|---|---|---|---|
| ① ตำแหน่ง | "พิมพ์ว่าอะไรใต้ลายเซ็น / ในรายงาน" | `personnel_assignments.position` (ข้อความ) | แสดงผลเท่านั้น **ไม่ให้สิทธิ์ใด ๆ** |
| ② ประเภทบุคลากร | "สถานภาพการจ้างคืออะไร" | `personnel_types` (หน้า ประเภทบุคลากร) | สิทธิ์วันลา (`leave_policies`) และรายงาน |
| ③ บทบาท (Role) | "ใช้โมดูล/ฟังก์ชันอะไรได้บ้าง" | Spatie roles + permissions | เข้าถึงเมนูและ API |
| ④ หน่วยงาน/การมอบหมาย | "เห็นข้อมูลของใคร / อนุมัติให้ใคร" | `org_units`, `personnel_assignments.org_unit_id`, `org_unit_managers`, `permission_scopes` | ขอบเขตข้อมูลและสายอนุมัติ |

ผลที่ได้:
- **ครูที่ได้รับแต่งตั้งเป็นหัวหน้างานพัสดุ** ยังเป็นประเภท "ข้าราชการ" (②) บทบาท "Employee" (③) แต่มีการมอบหมายเป็นหัวหน้า `งานพัสดุ` (④) — ไม่ต้องมี role ใหม่
- **ผู้บริหาร** ไม่ใช่ประเภทบุคลากร ผอ./รองฯ ส่วนใหญ่เป็นข้าราชการ (②) ความเป็นผู้บริหารมาจากบทบาท (③) + การเป็นหัวหน้าของ ROOT/ฝ่าย (④)
- **ครู vs เจ้าหน้าที่** ไม่มีผลต่อสิทธิ์การใช้ระบบในปัจจุบัน ต่างกันที่สถานภาพการจ้าง (②) และหน่วยงานที่สังกัด (④)

## 2. สภาพปัจจุบันในระบบ

ตรวจจากฐานข้อมูล local (เป็นข้อมูลทดสอบ **ต้องตรวจซ้ำบน production ก่อนลงมือ**) และโค้ด

| เรื่อง | ปัจจุบัน |
|---|---|
| Roles | `Super Admin`, `Director`, `Deputy Director`, `HR Head`, `Document Officer`, `Employee` |
| ประเภทบุคลากร | `civil_servant` ข้าราชการ · `government_employee` พนักงานราชการ · `permanent_employee` ลูกจ้างประจำ · `temporary_employee` ลูกจ้างชั่วคราว |
| หน่วยงาน | `ORG-ROOT` + หน่วยงานระดับเดียว (แบน) ใต้ ROOT |
| หัวหน้าหน่วยงาน (`org_unit_managers`) | 0 แถว — สายอนุมัติจึงตกไปใช้ fallback ตามชื่อ role/permission |
| ขอบเขตรายคน (`permission_scopes`) | 0 แถว |

## 3. โครงสร้างหน่วยงานที่เสนอ

ตามโครงสร้างการบริหารสถานศึกษาอาชีวศึกษา (4 ฝ่าย) — **ชื่อฝ่าย/งานต้องยืนยันกับระเบียบฉบับที่ผู้ใช้ถือใช้** ระบบไม่ hard-code ชื่อเหล่านี้ ผู้ดูแลกรอกเองในหน้าจัดการหน่วยงาน

```
ORG-ROOT  วิทยาลัย…                         หัวหน้า = ผู้อำนวยการ
├── ฝ่ายบริหารทรัพยากร                      หัวหน้า = รองผู้อำนวยการฝ่ายบริหารทรัพยากร
│   ├── งานบริหารงานทั่วไป (สารบรรณ)
│   ├── งานบุคลากร
│   ├── งานการเงิน
│   ├── งานการบัญชี
│   ├── งานพัสดุ
│   ├── งานอาคารสถานที่
│   ├── งานทะเบียน
│   └── งานประชาสัมพันธ์
├── ฝ่ายยุทธศาสตร์และแผนงาน                 หัวหน้า = รองฯ ฝ่ายยุทธศาสตร์และแผนงาน
│   └── งานวางแผนและงบประมาณ, งานศูนย์ข้อมูลสารสนเทศ, งานความร่วมมือ, งานวิจัยฯ, งานประกันคุณภาพฯ, งานส่งเสริมผลิตผลฯ …
├── ฝ่ายพัฒนากิจการนักเรียนนักศึกษา          หัวหน้า = รองฯ ฝ่ายพัฒนากิจการนักเรียนนักศึกษา
│   └── งานกิจกรรมฯ, งานครูที่ปรึกษา, งานปกครอง, งานแนะแนวอาชีพฯ, งานสวัสดิการฯ, งานโครงการพิเศษฯ …
└── ฝ่ายวิชาการ                             หัวหน้า = รองฯ ฝ่ายวิชาการ
    ├── แผนกวิชา… (ทุกแผนก)
    └── งานพัฒนาหลักสูตรฯ, งานวัดผลและประเมินผล, งานวิทยบริการและห้องสมุด, งานทวิภาคี, งานสื่อการเรียนการสอน …
```

**กฎความลึก (สำคัญ):** หน่วยงานต้นสังกัดของบุคลากรต้องอยู่ระดับ "งาน/แผนกวิชา" ใต้ฝ่ายโดยตรง เพราะ `ApproverResolverService::resolveDivisionDirectorIds()` หา "รองฯ" จาก **หัวหน้าของหน่วยงานแม่ของต้นสังกัด** และหา "ผอ." จากหัวหน้าของ ROOT (`backend/app/Services/Workflow/ApproverResolverService.php`) ถ้าซ้อนลึกกว่านี้ รองฯ จะกลายเป็นหัวหน้าระดับกลางผิดคน

## 4. ตารางจับคู่

คอลัมน์ "ขอบเขต" = ขอบเขตข้อมูลที่ได้ (`SELF`, `UNIT`, `DESCENDANTS`, `ORGANIZATION`) ตาม `OrgScopeResolver`

## 5. ข้อระวังจากโค้ดปัจจุบัน

### 5.1 การตั้งหัวหน้าหน่วยงาน **หรี่** ขอบเขตของคนนั้นทุกสิทธิ์
`OrgScopeResolver::visibleOrgUnitIds()` ตัดสินตามลำดับ: `permission_scopes` ของคนนั้น → **หน่วยงานที่เป็นหัวหน้า** → ค่าเริ่มต้นของจุดเรียก (รายการ/รายงานส่วนใหญ่ใช้ `ORGANIZATION`)

ผลคือ ถ้าตั้งหัวหน้างานบุคลากรเป็น `MANAGER` ของ `งานบุคลากร` เขาจะ **เห็นรายงานการลาได้แค่งานบุคลากร** แทนที่จะเห็นทั้งองค์กร ต้องเพิ่ม `permission_scopes` = `ORGANIZATION` ให้สิทธิ์งานบุคลากรของคนนั้น (`leave.report.view`, `leave.management.manage`, `attendance.view_all` ฯลฯ) ในวันเดียวกับที่ตั้งหัวหน้า
รองฯ ก็เช่นกัน: ปัจจุบัน Deputy Director มี `view_all_attendances` และเห็นทั้งองค์กร เมื่อตั้งเป็นหัวหน้าฝ่ายแล้วจะเห็นเฉพาะฝ่ายตน — **ต้องยืนยันว่าต้องการผลนี้ (Q6)**

### 5.2 ห้ามเปลี่ยนชื่อ role `Director`, `Deputy Director`, `HR Head`, `Super Admin`
โค้ดยังอ้างชื่อเหล่านี้ใน fallback สายอนุมัติ (`ApproverResolverService`), บล็อกลงนามของแบบฟอร์ม (`LeaveApproverBlocks`, `LeaveFormFieldMap`), รายการ role ที่ห้ามลบ (`Api/RoleController`) และ `Gate::before` ชื่อที่ผู้ใช้เห็นให้แก้ที่ `description` ไม่ใช่ `name`

### 5.3 สายอนุมัติตกไป fallback เมื่อยังไม่มีหัวหน้าหน่วยงาน
ตอนนี้ `org_unit_managers` ว่าง ระบบจึงหา "หัวหน้าแผนก / รองฯ / ผอ." จาก role หรือ permission แทน — **รองฯ ทุกคนอนุมัติได้ทุกฝ่าย** เมื่อตั้งหัวหน้าครบ สายอนุมัติจะแม่นตามฝ่าย ควรตั้งให้ครบทุกฝ่ายพร้อมกัน ไม่ทยอยทีละฝ่าย มิฉะนั้นบางฝ่ายแม่น บางฝ่ายยังเปิดกว้าง

### 5.4 หนึ่งคนมีต้นสังกัดได้หน่วยงานเดียว
`personnel_assignments` ที่มีผลอยู่เป็นต้นสังกัดเดียว ครูที่สังกัดแผนกวิชาแต่ทำงานพัสดุด้วยจะ "อยู่" แผนกวิชา งานพัสดุผูกได้เฉพาะในฐานะหัวหน้า (`org_unit_managers`) ถ้าต้องการ "สมาชิกงาน" หลายงานต่อคน ต้องเปลี่ยน schema (หัวข้อ 7)

### 5.5 การย้ายหน่วยงานไปใต้ฝ่าย
หน่วยงานปัจจุบันอยู่ใต้ ROOT โดยตรง การย้ายเข้าใต้ฝ่ายคือการเปลี่ยน `parent_id` ต้องทำผ่านหน้าจอที่บันทึก audit และ **ห้ามลบหน่วยงานเก่า** ที่มีประวัติผูกอยู่ (ปิดด้วย `effective_to` / `is_active` แทน)

### 5.6 ครูจ้างสอนกับสิทธิ์วันลา
ประเภทบุคลากรใหม่จะยังไม่มี `leave_policies` และ **ระบบไม่ปฏิเสธ** — `LeavePolicyService::resolve()` จะ **สร้าง policy ให้อัตโนมัติ** จาก `leave_types.max_days` (ค่ากลางที่ใกล้เคียงข้าราชการ) ในครั้งแรกที่มีการยื่นหรือคำนวณยอด ผลคือครูจ้างสอนอาจได้สิทธิ์ลาเท่าข้าราชการโดยไม่มีใครตั้งใจ

ดังนั้น **ต้องสร้าง `leave_policies` ของประเภทใหม่ให้ครบทุกประเภทการลาก่อนผูกบุคลากรคนแรก** โดยใช้จำนวนวันที่งานบุคลากรยืนยัน (ตามสัญญาจ้าง/ระเบียบที่ใช้) — เป็น stop condition "กฎราชการยังไม่มี policy ที่ชัดเจน"

### 6.1 คำตอบที่ได้รับแล้ว (2026-10-16)

**Q1 — ใช้โครงสร้าง 4 ฝ่ายตามหัวข้อ 3**
- ชื่อฝ่ายและงานในหัวข้อ 3 เรียบเรียงจากความรู้เดิมเรื่องระเบียบ สอศ. ว่าด้วยการบริหารสถานศึกษา **ไม่ได้ตรวจกับตัวระเบียบฉบับล่าสุด** ชื่องานบางงานอาจต่างไป
- ไม่กระทบระบบ: ชื่อหน่วยงานเป็นข้อมูลที่ผู้ดูแลแก้ได้จากหน้าจอภายหลัง โดยไม่ต้องแก้โค้ด สิ่งที่ต้องคงไว้คือ **ความลึก** (ROOT → ฝ่าย → งาน/แผนกวิชา) ตามกฎในหัวข้อ 3

**Q2 — ใช้ค่ากลางไปก่อน แล้วปรับภายหลัง**
- "ค่ากลาง" มีได้สองชุด ตัวเลขต่างกันมาก (จาก DB ทดสอบบนเครื่อง ต้องตรวจกับ production):

| ประเภทการลา | ก. ค่ากลางของระบบ (`leave_types.max_days` = ระดับข้าราชการ) | ข. คัดลอกจาก "ลูกจ้างชั่วคราว" |
|---|---|---|
| ลาป่วย | 120 | 30 |
| ลากิจส่วนตัว | 45 | 5 |
| ลาพักผ่อน | 10 | 6 |
| ลาคลอดบุตร | 90 | 45 |
| ลาอุปสมบท / ฮัจญ์ | 120 | ไม่มีสิทธิ์ |

- ก. คือสิ่งที่ระบบทำเองเมื่อไม่ได้สร้าง policy (ข้อ 5.6) ข. ใกล้เคียงสถานภาพจริงของครูจ้างสอนมากกว่า
- **ข้อเสนอ: ใช้ ข.** เพราะการปรับลดโควตาภายหลังทำให้บุคลากรที่ลาเกินโควตาใหม่ไปแล้วมียอดติดลบ ขณะที่การปรับเพิ่มภายหลังไม่มีผลเสีย
- ไม่ว่าเลือกชุดไหน ให้สร้าง `leave_policies` ของประเภทใหม่อย่างชัดเจน (ไม่ปล่อยให้ระบบสร้างเอง) โดยใช้ `effective_from` เป็นวันเริ่มใช้ เมื่อได้ตัวเลขจริงให้ปิดชุดเดิมด้วย `effective_to` และสร้างชุดใหม่ ห้ามแก้ทับ (PROJECT_RULES ข้อ 7)

## 7. สิ่งที่ต้องเปลี่ยน schema (ถ้าต้องการ)

ระบบอยู่ใน `PRODUCTION PHASE` ซึ่ง **ห้ามเปลี่ยน schema เว้นแต่แก้บั๊กร้ายแรง** ข้อต่อไปนี้จึงต้องได้รับอนุมัติแยก:

1. **กลุ่มบุคลากร (ผู้บริหาร / ครู / เจ้าหน้าที่)** สำหรับรายงาน — ยังไม่มีที่เก็บ ทางเลือก:
   - (ไม่เปลี่ยน schema) คำนวณ "ผู้บริหาร" จากการเป็นหัวหน้าของ ROOT/ฝ่าย และแยก ครู/เจ้าหน้าที่ จากหน่วยงานต้นสังกัด (แผนกวิชา = ครู) — ใช้ได้ถ้าเจ้าหน้าที่ไม่สังกัดแผนกวิชา
   - (เปลี่ยน schema) ตารางตำแหน่ง `positions` ที่มีกลุ่ม ตามที่ CORE-02 วางไว้ แล้วให้ `personnel_assignments` อ้างอิงแทนข้อความอิสระ
2. **สมาชิกหลายงานต่อคน** (ข้อ 5.4) — ต้องมีตารางการมอบหมายหน้าที่เพิ่ม

## 8. ขั้นตอนลงมือ (หลังตอบคำถามหัวข้อ 6 แล้ว)

1. สำรองฐานข้อมูล production
2. สร้างฝ่ายและงานตามหัวข้อ 3; ย้ายหน่วยงานเดิมเข้าใต้ฝ่าย (ข้อ 5.5)
3. เพิ่มประเภทบุคลากรใหม่ (ถ้ามี) และสร้าง `leave_policies` ครบทุกประเภทการลาตามที่งานบุคลากรยืนยัน **ก่อน** ผูกบุคลากร (ข้อ 5.6)
4. ตั้งต้นสังกัดและตำแหน่งของบุคลากรทุกคน
5. ตั้งหัวหน้าหน่วยงาน (ROOT, ทุกฝ่าย, ทุกแผนกวิชา/งานที่มีผู้อนุมัติ) **พร้อมกันทั้งหมด** และเพิ่ม `permission_scopes` ให้งานบุคลากรในวันเดียวกัน (ข้อ 5.1, 5.3)
6. ตรวจด้วยบัญชีตัวอย่างหนึ่งคนต่อแถวในหัวข้อ 4: เมนูที่เห็น, รายงานที่เห็น, สายอนุมัติใบลา

**Automated tests ที่ต้องมี** (ตาม CLAUDE.md — business rule + authorization):
- ครูแผนกวิชา A ยื่นลา → ผู้อนุมัติคือ หัวหน้าแผนก A → รองฯ วิชาการ → ผอ. (ไม่ใช่รองฯ ฝ่ายอื่น)
- เจ้าหน้าที่งานพัสดุยื่นลา → รองฯ บริหารทรัพยากร
- รองฯ ฝ่าย X เปิดใบลา/รายงานของฝ่าย Y ไม่ได้ (IDOR)
- หัวหน้างานบุคลากรที่ถูกตั้งเป็นหัวหน้างานและมี `permission_scopes` = ORGANIZATION ยังเห็นรายงานทั้งองค์กร
- หัวหน้าที่ `effective_to` ผ่านไปแล้วอนุมัติ/มองเห็นไม่ได้
- ครูจ้างสอนได้โควตาวันลาตาม `leave_policies` ของประเภทตน ไม่ใช่ค่ากลางจาก `leave_types.max_days` (ข้อ 5.6)
