# แผนยกระดับการตั้งค่าแบบฟอร์มลาเป็น Visual PDF Template Designer

วันที่วิเคราะห์ 2026-09-08 · ขอบเขต: อ่านโค้ดและ migration ที่มีอยู่จริงในสาขาปัจจุบัน · ไม่มีการแก้ application code, schema หรือข้อมูลในรอบนี้

## 1. ข้อสรุป

**ยังไม่สมบูรณ์ — ปัจจุบันอยู่ระดับ MVP ของ visual designer ไม่ใช่ Visual PDF Template Designer เต็มรูปแบบ**

สิ่งที่เป็นจริงตอนนี้:

- มีหน้าออกแบบวางฟิลด์บน PDF จริงอยู่แล้ว (`frontend/src/views/admin/DocumentDesignerView.vue`) ลาก/ปรับขนาด/หลายหน้า/พรีวิว/ออกเวอร์ชัน/เผยแพร่/เลิกใช้ ได้
- โครงหลังบ้านออกแบบเป็น engine กลางที่ไม่ผูกกับโมดูลลาแล้ว (`DocumentEngine`, `TemplateResolver`, `DataProviderRegistry`, `document_binding_rules` มีคอลัมน์ `module`/`entity_type`) จึงรองรับแบบฟอร์มโมดูลอื่นได้ในเชิงสถาปัตยกรรม
- แต่ **การตั้งค่าแบบฟอร์มลารายประเภทยังไม่ได้เชื่อมถึง designer แบบครบวงจร**: engine ปิดอยู่ใน runtime, เปิดรายประเภทได้จาก `.env` เท่านั้น และ 8 จาก 9 แม่แบบลายังไม่มีเวอร์ชัน (หลักฐาน `docs/checkpoints/LEAVE-SETTINGS-FORMS-AUDIT-2026-09-07.md` ข้อ LS-08)
- ความสามารถหลายอย่างที่ renderer/API รองรับแล้ว **ยังไม่มีปุ่มให้ผู้ดูแลใช้** และบางชนิดฟิลด์ที่ UI ให้เลือก **renderer ยังไม่รองรับจริง**

สรุปสั้น: เป็น "ตัววางพิกัดฟิลด์" ที่ใช้ได้ แต่ยังไม่ใช่ "เครื่องมือออกแบบแบบฟอร์ม" ที่ผู้ดูแลระบบใช้จบงานเองได้โดยไม่ต้องพึ่งผู้พัฒนา

## 2. สิ่งที่มีอยู่แล้ว (ตรวจจากโค้ด)

| ความสามารถ | สถานะ | หลักฐาน |
|---|---|---|
| อัปโหลด PDF ต้นฉบับเป็นพื้นหลัง | มี (เฉพาะฉบับร่าง) | `DocumentEngineController::uploadPdf` |
| ลาก/ปรับขนาดกล่องฟิลด์ด้วยเมาส์ | มี | `DocumentDesignerView.vue` (`startDrag`/`startResize`) |
| ทำงานหลายหน้า | มี (เลือกหน้าจากปุ่มเลข) | `pageCount`, `pageMappings` |
| ย่อ/ขยายมุมมอง 50–200% | มี | `zoom` |
| แก้พิกัด/ขนาด/ฟอนต์ไซซ์/จัดวาง/หน้า ด้วยตัวเลข | มี | panel "คุณสมบัติฟิลด์" |
| รายการตัวแปร (Field Dictionary) + ค้นหา + จัดกลุ่ม | มี (อ่านอย่างเดียว) | `GET /admin/document-engine/fields` |
| พรีวิว PDF จากค่าตัวอย่าง | มี | `DocumentEngine::preview` |
| เวอร์ชันแบบฟอร์ม + effective dating + publish/retire + ห้ามแก้ฉบับที่เผยแพร่ | มี | `publishVersion`, `retireVersion`, `saveMappings` (abort เมื่อไม่ใช่ DRAFT) |
| pin เวอร์ชันกับเอกสารที่ออกไปแล้ว | มี | `TemplateResolver::versionForDocument`, `leaves.document_template_version_id` |
| กติกาผูกแบบฟอร์มกับ entity + priority + ช่วงมีผล | มี | `document_binding_rules`, `TemplateResolver::resolveTemplate` |
| ค่าชดเชยการพิมพ์ (GLOBAL/TEMPLATE/USER) | มี (อยู่คนละหน้า) | `DocumentCenterView.vue` แท็บ "ตั้งค่าการพิมพ์" |
| เก็บไฟล์ที่ออกแล้วเป็น revision + sha256 + snapshot | มี | `DocumentEngine::store` |
| audit ทุกการกระทำของ designer | มี | `AuditLogger` ในทุก endpoint |
| ถอยกลับเส้นทางเดิมอัตโนมัติเมื่อ engine ล้ม | มี | `LeaveDocumentGateway::pdfFor` |

## 3. ช่องว่างที่ยืนยันจากโค้ด

### กลุ่ม A — ความถูกต้องของการวางตำแหน่ง (P0 ต้องแก้ก่อนเปิดใช้จริง)

- **A1 · ขนาดหน้ากระดาษถูก hard-code 595×842 pt**
  `DocumentDesignerView.vue` ตรึง A4 แนวตั้งเสมอ (`pageWidth`/`pageHeight`) ขณะที่ `PdfOverlayRenderer::render` ใช้ขนาดจริงของหน้าที่ import (`getTemplateSize`) แบบฟอร์ม F4/Legal/แนวนอน/ไฟล์สแกนที่ไม่ใช่ 595×842 จะวางบนจอตำแหน่งหนึ่งแต่พิมพ์ออกอีกตำแหน่งหนึ่ง และผิดไม่เท่ากันในแต่ละหน้าของไฟล์เดียวกันได้
- **A2 · พื้นหลังเป็น `<iframe>` ของโปรแกรมอ่าน PDF ในเบราว์เซอร์ (`#view=Fit`)**
  ระบบไม่ได้ควบคุมสเกล/ระยะขอบที่เบราว์เซอร์ใช้เรนเดอร์ กล่องฟิลด์ที่ซ้อนทับจึง "ดูตรง" โดยไม่มีอะไรรับประกันว่าตรงจริง และผลอาจต่างกันระหว่างเบราว์เซอร์
- **A3 · ไม่มี snap/grid/ไม้บรรทัด/นัดจ์ด้วยลูกศร/จัดแนวหลายฟิลด์/คัดลอกฟิลด์**
  แบบฟอร์มราชการเป็นตารางเส้นตรง งานวางจึงต้องเล็งด้วยตาทีละกล่อง ใช้เวลามากและคลาดเคลื่อนสะสม
- **A4 · ไม่มี undo/redo และไม่เตือนเมื่อออกจากหน้าโดยยังไม่บันทึก**

### กลุ่ม B — ความสามารถที่หลังบ้านมีแล้วแต่ไม่มีใน UI

- **B1 · panel คุณสมบัติขาด `font`, `overflow`, `format`, `static_text`, `options`**
  ทั้งห้าคอลัมน์มีในตาราง `document_field_mappings` มีใน validation ของ `saveMappings` และ renderer ใช้จริง (เช่น `options['mark']` ของช่องติ๊ก, `overflow = shrink`) แต่ designer ส่งค่า default/null เสมอ ผู้ดูแลจึงตั้งตัวหนา ข้อความคงที่ รูปแบบวันที่ หรือเครื่องหมายติ๊กเองไม่ได้
- **B2 · `format` ไม่ถูกนำไปใช้ใน renderer เลย**
  `PdfOverlayRenderer::draw` ไม่อ่าน `$mapping->format` ค่าที่เก็บไว้จึงไม่มีผล — ต้องทำ formatter (วันที่ พ.ศ., เลขไทย, ทศนิยม) ให้ครบคู่กับ B1
- **B3 · `QR_CODE` และ `BARCODE` เลือกได้ใน UI แต่ renderer วาดเป็นข้อความธรรมดา**
  `DocumentFieldDefinition::TYPES` และ `fieldTypes` ใน designer มีสองชนิดนี้ แต่ `draw()` ไม่มี branch รองรับ จึงตกไปที่ `drawText` — ผู้ดูแลตั้งค่าได้แต่ได้ผลผิดโดยไม่มีคำเตือน

### กลุ่ม C — การรองรับแบบฟอร์มเฉพาะประเภทลา

- **C1 · ช่องเพิ่มเติมรายประเภท (`leave_types.extra_fields`) ไม่ปรากฏใน Field Dictionary**
  `LeaveDocumentFields::extra()` สร้างค่าไว้ให้แล้วและ provider ส่งต่อเข้า values แต่ `LeaveRequestDataProvider::catalog()` / `DocumentEngineSeeder` ไม่ได้ประกาศฟิลด์เหล่านี้ designer จึงไม่มีปุ่มให้วาง "ชื่อภริยา / วันคลอด / ชื่อวัด / หลักสูตร" ลงแบบฟอร์ม ทั้งที่ข้อมูลมีอยู่
- **C2 · ผู้ดูแลเพิ่มฟิลด์ในพจนานุกรมเองไม่ได้** — มีเฉพาะ `GET /fields` ไม่มี POST/PUT/DELETE
- **C3 · `approval.step{N}.*` ไม่มีในแคตตาล็อก** ทั้งที่ provider สร้างค่าให้ตามจำนวนขั้นจริง แบบฟอร์มที่มีบล็อกลงนาม 3–4 ขั้นจึงวางได้แค่ขั้นแรกกับขั้นสุดท้าย
- **C4 · ไม่มีชนิด "กลุ่มช่องติ๊ก" และ "ตารางซ้ำ"** — ตารางสถิติการลาแบบราชการต้องวางทีละช่องหลายสิบกล่อง และไม่มีเงื่อนไขแสดง/ซ่อนตามค่าข้อมูล
- **C5 · การเปิดใช้ engine รายประเภทลาอยู่ใน `.env`** (`config/document_engine.php`) ผู้ดูแลเปิดจากหน้าจอไม่ได้ ไม่มี audit และ runtime ปัจจุบันยังปิดทั้งระบบ

### กลุ่ม D — คุณภาพงานและการตรวจก่อนเผยแพร่

- **D1 · พรีวิวใช้ค่าตัวอย่างที่เป็น "ชื่อโค้ดของฟิลด์"** (`DocumentEngine::sampleValue`) ตรวจความยาวจริง การล้นช่อง หรือการตัดบรรทัดไม่ได้ และไม่มีโหมดพรีวิวจากใบลาจริงหนึ่งใบ
- **D2 · ไม่มีการตรวจก่อนเผยแพร่**: ฟิลด์ทับกัน ฟิลด์อยู่นอกขอบกระดาษ `page` เกิน `page_count` `field_code` ที่ไม่มีในพจนานุกรม หรือฟิลด์บังคับที่ยังไม่ได้วาง — เผยแพร่ผ่านได้ทั้งหมด
- **D3 · ค่าชดเชยการพิมพ์อยู่คนละหน้ากับ designer และไม่มีใบสอบเทียบ (test print sheet)** ผู้ดูแลจึงหาค่า x/y offset ด้วยการเดา
- **D4 · ไม่มี import/export ชุดแบบฟอร์มจากหน้าจอ** (มีเฉพาะคำสั่ง CLI `document:import-form-templates`) ย้ายแบบฟอร์มข้ามเครื่อง/สถานศึกษาไม่ได้
- **D5 · ไม่มีเทสต์ยืนยันความเที่ยงของพิกัด** — `DocumentEngineTest` ครอบ flow และสิทธิ์ แต่ไม่มีเทสต์ที่ยืนยันว่าพิกัดที่บันทึกออกมาตรงตำแหน่งใน PDF และไม่มีเทสต์ฝั่ง UI ของ designer

### กลุ่ม E — การรองรับแบบฟอร์มโมดูลอื่นในอนาคต

- **E1 · รายการ entity ในหน้าผูกแบบฟอร์ม hard-code เฉพาะ LEAVE**
  `DocumentEngineController::bindings()` คืน `entities` เป็น `['LEAVE' => ['LEAVE_TYPE' => ..., 'LEAVE_CANCELLATION' => ...]]` โมดูลใหม่ (สารบรรณ พัสดุ การเงิน บุคลากร) จะผูกแบบฟอร์มจากหน้าจอไม่ได้จนกว่าจะแก้โค้ดตรงนี้
- **E2 · ไม่มี gateway กลาง** — `LeaveDocumentGateway` เป็นของโมดูลลาโดยเฉพาะ โมดูลใหม่ต้องเขียน gateway ของตัวเองซ้ำทั้งชุด (ธงเปิด/ปิด, fallback, finalize, pin version)
- **E3 · ยังไม่มีสัญญาการต่อขยายที่เป็นลายลักษณ์อักษร** ว่า "จะเพิ่มแบบฟอร์มของโมดูลใหม่ต้องทำอะไรบ้าง" ใน `docs/MODULE-EXTENSION-GUIDE.md` / `docs/14-DOCUMENT-PDF-STANDARDS.md`
- **E4 · ฟอนต์ตรึงไว้ 2 ตัวและเข้ารหัส cp874** (`PdfOverlayRenderer`) อักขระนอก cp874 หายเงียบ ๆ และไม่มีสี/ตัวหนา/ขีดเส้นใต้/ข้อความหมุน ซึ่งแบบฟอร์มบางประเภทต้องใช้

## 4. แผนทำให้สมบูรณ์

แบ่งเป็น 5 ระยะ ทำตามลำดับได้ และหยุดพักได้ทุกปลายระยะโดยระบบยังใช้งานได้ปกติ

### ระยะ 1 — ความถูกต้องของพิกัด (P0 ต้องจบก่อนเปิด engine)

1. เปลี่ยนพื้นหลัง designer จาก `<iframe>` เป็น **pdf.js render ลง `<canvas>`** อ่านขนาดหน้าจริงรายหน้า (`getViewport`) แล้วใช้ค่านั้นเป็นระบบพิกัดของ canvas แทนค่าคงที่ 595×842
2. เก็บ `page_width`/`page_height` รายหน้าไว้ที่เวอร์ชันตอนอัปโหลด PDF เพื่อให้ฝั่ง server ตรวจซ้ำได้ว่าฟิลด์อยู่ในหน้ากระดาษ
3. เพิ่ม snap-to-grid ปรับระยะได้, ไม้บรรทัด, นัดจ์ด้วยปุ่มลูกศร (1pt / Shift 10pt), เลือกหลายฟิลด์แล้วจัดแนว–กระจายระยะ, คัดลอก–วาง, ทำซ้ำไปหน้าอื่น
4. undo/redo และเตือนก่อนออกจากหน้าเมื่อมีการแก้ที่ยังไม่บันทึก
5. เทสต์: unit ของตัวแปลงพิกัด + feature test ที่ยืนยันว่าฟิลด์นอกขอบกระดาษถูกปฏิเสธ

**DoD:** วางฟิลด์บนแบบฟอร์มที่ไม่ใช่ A4 แล้วพิมพ์ออกมาตรงตำแหน่งเท่าที่เห็นบนจอ ยืนยันด้วยการวัดจากไฟล์ผลลัพธ์

### ระยะ 2 — เปิดความสามารถที่หลังบ้านมีอยู่แล้ว (P1)

1. เพิ่มใน panel คุณสมบัติ: ฟอนต์ (ปกติ/หนา), การล้น (shrink/wrap/clip), รูปแบบค่า (`format`), ข้อความคงที่, ตัวเลือกเฉพาะชนิด (เครื่องหมายติ๊ก, ค่าที่ถือว่าติ๊ก)
2. ทำ **formatter กลาง** ให้ `format` มีผลจริงใน renderer: วันที่ไทย/พ.ศ., เลขไทย, ทศนิยม, จำนวนเงิน, การจัดรูปข้อความ
3. รองรับ `QR_CODE`/`BARCODE` ใน renderer จริง หรือถ้ายังไม่ทำ ให้ **ตัดออกจากตัวเลือกใน UI และ validation** จนกว่าจะรองรับ — ห้ามให้เลือกสิ่งที่ระบบทำไม่ได้
4. เพิ่มการวาดที่แบบฟอร์มราชการต้องใช้: ตัวหนา, ขีดเส้นใต้, ระยะห่างตัวอักษร (ช่องกรอกทีละตัวอักษร), ข้อความหมุน 90°

**DoD:** ทุกตัวเลือกที่กดได้ใน UI มีผลจริงในไฟล์ PDF ที่ออก และมีเทสต์คู่กับทุกชนิดฟิลด์

### ระยะ 3 — ครบวงจรกับการตั้งค่าประเภทการลา (P1)

1. **ผลักช่องเพิ่มเติมของประเภทลาเข้า Field Dictionary อัตโนมัติ** — เมื่อผู้ดูแลเพิ่ม extra field ที่ `LeaveTypesManagementView` ให้เกิด `document_field_definitions` code `extra.<key>` พร้อม `data_type` ตามที่นิยาม (ต้องแก้ validation ของ `StoreLeaveRequest` ให้ตรวจชนิดจริงด้วย ตามข้อค้างจาก audit)
2. เพิ่ม `approval.step1..N` เข้าแคตตาล็อกตามจำนวนขั้นสูงสุดของสายอนุมัติจริง
3. เพิ่ม CRUD ของ Field Dictionary สำหรับผู้มีสิทธิ์ `document.template.manage` เฉพาะฟิลด์ที่ผูกกับ data source ที่ลงทะเบียนแล้ว — ห้ามรับนิพจน์หรือ SQL อิสระจาก UI
4. เพิ่มชนิด **กลุ่มช่องติ๊ก** (หนึ่งฟิลด์ ↔ หลายพิกัดตามค่า) และ **บล็อกตารางซ้ำ** สำหรับตารางสถิติการลา พร้อมเงื่อนไขแสดง/ซ่อนแบบ whitelist (เท่ากับ / ไม่เท่ากับ / ว่าง)
5. ย้ายสวิตช์เปิด engine รายประเภทลาจาก `.env` มาเป็น **ค่าตั้งค่าในฐานข้อมูล + audit** โดยคงธง `.env` ไว้เป็น kill switch ระดับบนสุด
6. ในหน้า `LeaveTypesManagementView` แสดงสถานะแบบฟอร์มของแต่ละประเภท (ผูกแม่แบบใด เวอร์ชันใด เผยแพร่หรือยัง) พร้อมลิงก์ตรงไป designer

**DoD:** ผู้ดูแลเพิ่มประเภทลาใหม่ + ช่องเฉพาะ + อัปโหลดแบบฟอร์ม + วางฟิลด์ + เผยแพร่ + เปิดใช้ ได้ครบโดยไม่ต้องแตะ `.env` หรือโค้ด

### ระยะ 4 — ตรวจสอบและควบคุมคุณภาพก่อนเผยแพร่ (P1)

1. **พรีวิวสามโหมด**: ค่าตัวอย่างสมจริง (ความยาวข้อความตามกรณีจริงที่ยาวที่สุด), ใบลาจริงที่เลือกเอง (อ่านอย่างเดียว + audit), และโหมดโครงเปล่าสำหรับตรวจแนวเส้น
2. **ตรวจก่อนเผยแพร่ (pre-publish check) ที่ฝั่ง server**: ฟิลด์ทับกัน, เกินขอบ, `page` เกินจำนวนหน้า, `field_code` ไม่มีในพจนานุกรม, ฟิลด์บังคับของ entity ที่ยังไม่ได้วาง → เตือนหรือปฏิเสธตามระดับความรุนแรง
3. **ใบสอบเทียบการพิมพ์** — พิมพ์หน้าที่มีกากบาทพิกัดรู้ค่า ให้ผู้ดูแลวัดแล้วกรอกค่าคลาดเคลื่อน ระบบคำนวณ `x_offset/y_offset/scale` ให้ และย้ายการตั้งค่านี้เข้ามาในหน้า designer ด้วย
4. **เทียบเวอร์ชัน (diff)** — เห็นว่าเวอร์ชันใหม่ต่างจากเวอร์ชันก่อนที่ฟิลด์ใดก่อนกดเผยแพร่
5. **นำเข้า/ส่งออกชุดแบบฟอร์ม** เป็นแพ็กเกจ (PDF ต้นฉบับ + mapping JSON + checksum) พร้อมตรวจไฟล์ตาม `config/uploads.php`

**DoD:** เผยแพร่แบบฟอร์มที่มีฟิลด์นอกกระดาษหรือทับกันไม่ได้ และมีเทสต์ครอบทุกกติกาตรวจ

### ระยะ 5 — เปิดใช้งานจริงกับแบบฟอร์มลา (P0 เชิงข้อมูล)

1. ตรวจสอบและกู้ประวัติเวอร์ชันของ 8 แม่แบบที่ยังไม่มีเวอร์ชัน (LS-08) — **ห้ามเติมเวอร์ชันปัจจุบันให้เอกสารย้อนหลังโดยเดา**
2. ปิด LS-04 (เวอร์ชันที่ pin ต้องเป็นตัวกำหนดชนิดและเนื้อหาเอกสารเก่า) ก่อนเปิด engine มิฉะนั้นการเปลี่ยนการผูกแบบฟอร์มจะย้อนกระทบใบเก่า
3. วางฟิลด์และเผยแพร่แบบฟอร์มทีละประเภท แล้วเปิด engine ทีละประเภทพร้อมเกณฑ์รับ (เทียบกับใบลาที่ออกด้วยเส้นทางเดิมอย่างน้อย 5 ใบต่อประเภท)
4. อัปเดต `docs/TRACEABILITY-MATRIX.md`, `docs/CHANGELOG.md`, `docs/14-DOCUMENT-PDF-STANDARDS.md` และบันทึก `docs/DECISION-LOG.md`

## 5. การรองรับแบบฟอร์มอื่นในอนาคต

เป้าหมาย: เพิ่มแบบฟอร์มของโมดูลใหม่ (สารบรรณ พัสดุ การเงิน บุคลากร คำสั่ง/ประกาศ/เกียรติบัตร) โดย **ไม่ต้องแก้ designer และไม่ต้องแก้ engine**

### 5.1 โครงกลางที่ต้องเพิ่ม

1. **ตารางแคตตาล็อก entity** (`document_entity_types`) แทนการ hard-code ใน `bindings()`
   เก็บ `module`, `entity_type`, `label_th` และวิธีดึงรายการตัวเลือก (อ้าง provider ที่ลงทะเบียนแล้วเท่านั้น) — หน้าผูกแบบฟอร์มอ่านจากตารางนี้
2. **`DocumentGateway` กลาง** ยกตรรกะที่ซ้ำออกจาก `LeaveDocumentGateway`: ธงเปิด/ปิดรายโมดูล, คืนไฟล์ฉบับสมบูรณ์ก่อน, เคารพเวอร์ชันที่ pin, fallback เมื่อล้ม, finalize ตามสถานะ — โมดูลใหม่ implement เฉพาะส่วนที่ต่าง
3. **Provider contract ที่บังคับ `catalog()`** เพื่อให้ฟิลด์ของโมดูลใหม่โผล่ในพจนานุกรมอัตโนมัติเมื่อ sync (ปัจจุบันมี `catalog()` อยู่แล้วแต่ไม่ได้บังคับใน interface)
4. **ธงเปิด/ปิดรายโมดูล** ใน `config/document_engine.php` เป็น `modules.<code>` แทนที่จะมีเฉพาะ `entities.leave_types`
5. **สิทธิ์รายโมดูล** — `document.template.manage` ปัจจุบันครอบทุกโมดูล ควรเพิ่ม scope รายโมดูลเมื่อมีโมดูลที่สองขึ้นไป ตาม `docs/06-RBAC-ABAC.md`

### 5.2 ขั้นตอนมาตรฐานของการเพิ่มแบบฟอร์มใหม่ (หลังทำ 5.1 แล้ว)

1. เขียน data provider หนึ่งคลาส implement `DocumentDataProvider` พร้อม `catalog()`
2. ลงทะเบียนใน `DataProviderRegistry::PROVIDERS` — คงกติกา whitelist ไว้ ห้ามอ่านชื่อคลาสจากฐานข้อมูล
3. เพิ่มแถวใน `document_entity_types` ผ่าน migration ของโมดูลนั้น
4. ผู้ดูแลสร้างแม่แบบ อัปโหลด PDF วางฟิลด์ ตรวจ พรีวิว และเผยแพร่ จากหน้าจอ
5. ผูก entity กับแม่แบบด้วย binding rule พร้อมช่วงมีผล
6. เปิดธงของโมดูลนั้น แล้ววัดผลตามเกณฑ์รับ

เขียนขั้นตอนนี้ลง `docs/MODULE-EXTENSION-GUIDE.md` และ `docs/14-DOCUMENT-PDF-STANDARDS.md` ให้เป็นสัญญาที่ตรวจได้

## 6. ข้อควรระวังและสิ่งที่ต้องตัดสินใจก่อนเริ่ม

- **ระบบอยู่ใน `PRODUCTION PHASE`** ตาม `CURRENT_PHASE.md` และ `PROJECT_RULES.md` ห้ามแก้ schema เว้นแต่เป็น Critical Bug Fix — ระยะ 1, 3 และ 5.1 มีตาราง/คอลัมน์ใหม่ จึงต้องได้รับอนุมัติเปิด phase ใหม่ และบันทึกใน `docs/DECISION-LOG.md` ก่อนลงมือ
- **ห้ามแก้เวอร์ชันที่เผยแพร่แล้ว** ทุกการเปลี่ยนต้องเป็นเวอร์ชันใหม่ (PROJECT_RULES ข้อ 7)
- **ห้ามเปิด engine ก่อนปิด LS-04 และ LS-08** มิฉะนั้นเอกสารย้อนหลังจะเปลี่ยนรูปแบบตามการตั้งค่าปัจจุบัน
- pdf.js เป็น dependency ใหม่ฝั่งหน้าเว็บ ต้องตรวจกับ `docs/02-TECH-STACK.md` และนโยบายไฟล์/CSP ก่อน
- ต้องเลือกว่าจะรองรับ `QR_CODE`/`BARCODE` จริงในระยะ 2 หรือถอดออกจาก UI ชั่วคราว — คงไว้แบบใช้ไม่ได้ไม่ใช่ตัวเลือก
