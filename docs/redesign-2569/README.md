## ลำดับการทำ

```
เฟส 0 (ตัดสิน) ─► เฟส 1 (ข้อมูล) ─► เฟส 3 (สายอนุมัติ) ─► เฟส 2 (กฎการลา) ─► เฟส 4 (บุคลากร) ─► เฟส 5 (ledger) ─► เฟส 6 (เปิดใช้)
                      └──────────── มาตรฐานภาษาไทย (07) ทำคู่ขนานได้ตลอด ────────────┘
```

- เฟส 1 และ 3 มาก่อน 2 เพราะปิดความเสี่ยงที่ใหญ่ที่สุดตอนใช้งานจริง: **ได้วันลาเกินสิทธิ์** และ **อนุมัติผิดคน**
- เฟส 5 ทำหลังเฟส 2 เพราะกฎใหม่ (การแปลงประเภทการลา การเรียกตัวกลับ) ต้องเขียนลง ledger ตั้งแต่แรก ถ้าทำ ledger ก่อนจะต้องแก้สองรอบ จึงออกแบบ ledger ไว้ในเอกสารนี้ก่อน และให้เฟส 2 เรียกผ่าน `LeaveLedgerService` ที่เริ่มจาก **เขียนคู่ขนาน** (ดู 05 หัวข้อ 4)
- แต่ละเฟสเป็น PR แยก มี automated test ของ business rule และ authorization ตาม CLAUDE.md

## หลักการที่ใช้ทุกเฟส

1. **กฎราชการเป็นข้อมูลที่มีรุ่น** (`effective_from` / `effective_to`) ไม่เขียนตายในโค้ด ค่าที่ยังไม่มีเอกสารยืนยันให้ระบบ **ปฏิเสธ** ไม่เดาค่าให้
2. **อำนาจอนุมัติมาจากคำสั่งมอบหมาย** (`org_unit_managers`, `user_delegations`) ไม่มาจากชื่อบทบาทหรือชื่อตำแหน่ง
3. **ไม่ลบ ไม่เขียนทับประวัติ** ใช้รายการกลับ (reversal) และการปิดช่วงเวลาแทน
4. **ข้อความที่ผู้ใช้เห็นเป็นภาษาไทยทั้งหมด** รวมข้อความ error, สถานะ, แจ้งเตือน, PDF, CSV (ดู 07)
5. migration เท่านั้นในการเปลี่ยน schema และต้องย้อนกลับได้โดยไม่ทำข้อมูลหาย
