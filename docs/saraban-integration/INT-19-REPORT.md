### 1. "ไม่มีปุ่มลบ" ไม่เท่ากับ "ลบไม่ได้"

ระบบเดิมไม่มี `destroy` ใน `DocumentController` อยู่แล้ว — แต่นั่นแปลว่า
**ยังไม่ได้ทำ** ไม่ใช่ **ห้ามทำ** · วันหนึ่งจะมีคนเพิ่ม endpoint นั้น หรือเรียก
`$document->delete()` จาก tinker, seeder, หรือ job ที่ตั้งใจดี

ด่านจึงอยู่ที่ **`Document::booted()`** ซึ่งเป็นจุดที่ทุกเส้นทางต้องผ่าน
หนังสือที่ `finalized_at` มีค่า หรือมีเลขที่หนังสือ หรือสถานะ `signed`
ลบไม่ได้ไม่ว่าเรียกจากที่ใด · ฉบับร่างยังลบได้ตามปกติ

เทสต์เรียก `$document->delete()` ตรง ๆ จาก PHP ไม่ผ่าน HTTP — เพราะสิ่งที่
ต้องพิสูจน์คือด่านที่ระดับโมเดล ไม่ใช่การไม่มี route

### 2. การอายัดชนะกำหนดการทำลายเสมอ

เอกสารที่อยู่ระหว่างคดีความหรือการสอบสวนต้องถูกแช่ไว้ **แม้ครบกำหนดทำลายและ
ได้รับอนุมัติมาก่อนหน้าแล้วก็ตาม**

เทสต์ `a held document cannot be disposed even when due and approved` เดินลำดับ
ที่อันตรายที่สุด: กำหนดอายุ → ครบกำหนด → **อนุมัติ** → *แล้วค่อยอายัด* →
สั่งทำลาย · ต้องถูกปฏิเสธ และไฟล์ต้องยังอยู่

ตรวจเงื่อนไขการอายัด **เป็นข้อสุดท้าย** โดยตั้งใจ เพื่อให้ข้อความที่ผู้ใช้เห็น
ตรงกับเหตุผลที่แท้จริงที่สุด (ไม่ใช่บอกว่า "ยังไม่อนุมัติ" ทั้งที่ปัญหาจริงคือถูกอายัด)

### 3. ทำลายไฟล์ ไม่ทำลายทะเบียน

> ทะเบียนที่ลบตัวเองพร้อมเอกสารคือทะเบียนที่ใช้ตรวจสอบไม่ได้

การทำลายลบ **ไฟล์** ทุกเวอร์ชันออกจาก storage แต่:

- แถว `saraban_documents` ยังอยู่ครบ
- แถว `saraban_retention_schedules` บันทึกว่าใครทำลาย เมื่อใด เพราะอะไร
- `disposed_file_hash` = SHA-512 ของ hash ทุกไฟล์ที่ถูกทำลายต่อกัน —
  **หลักฐานเดียวที่เหลือว่าไฟล์ที่ถูกทำลายคือไฟล์ไหน**

### 4. อนุมัติกับลงมือทำลายเป็นคนละการกระทำ (SoT §26)

แยกเป็นคนละ endpoint คนละสิทธิ์โดยตั้งใจ:

| ขั้น | สิทธิ์ | step-up |
|---|---|---|
| กำหนดอายุการเก็บ | `saraban.config.manage` | — |
| **อนุมัติให้ทำลาย** | `saraban.policy.manage` | ✅ |
| **ลงมือทำลาย** | `saraban.config.manage` | ✅ |

ผู้อนุมัติกับผู้ลงมือจึงไม่จำเป็นต้องเป็นคนเดียวกัน และการอนุมัติล่วงหน้า
ไม่ได้ทำลายอะไรทันที · ทั้งสองขั้นต้องยืนยันตัวตนซ้ำ (SoT §24)

### 5. รายงานคือทางลัดที่ข้ามขอบเขตได้ง่ายที่สุด

รายงานรวมข้อมูลจำนวนมากไว้ในคำขอเดียว — ถ้าไม่กรองขอบเขต **การควบคุมสิทธิ์
ทั้งหมดที่ทำมา 18 เช็คพอยต์จะไร้ความหมายด้วยคำขอเดียว**

ทะเบียนหนังสือและสรุปการเวียนจึงกรองด้วย `OrgScopeResolver` เหมือนหน้าทะเบียนปกติ
· หน้าจอบอกตรง ๆ ว่ารายงานถูกจำกัดตามขอบเขต เพื่อไม่ให้ผู้ใช้คิดว่าระบบนับผิด

**ข้อยกเว้นที่ตั้งใจ: รายงานเลขหนังสือไม่กรองหน่วยงาน** — เลขเป็นทรัพยากรร่วม
ของชุดเลขนั้น ผู้ตรวจสอบต้องเห็นช่องว่างในลำดับได้ ไม่งั้นแยกไม่ออกว่าเลขที่หายไป
เป็นการคืนเลขปกติหรือความผิดปกติ (สิทธิ์ `saraban.report.view` ยังบังคับอยู่)

### 6. รายงานการเวียนแยก "ยังไม่เปิด" ออกจาก "ยังไม่รับทราบ"

ตาม SoT §15 สองอย่างนี้ต่างกัน และผู้บริหารต้องเห็นความต่าง:

| ตัวเลข | ความหมาย |
|---|---|
| `never_opened` | ยังไม่เห็นหนังสือเลย |
| `not_acknowledged` | **รวมคนที่เปิดอ่านแล้วแต่ยังไม่กดรับทราบ** |

คนที่เปิดอ่านแล้วไม่กดรับทราบคือคนที่ *รู้แล้วแต่ยังไม่ยืนยัน* ซึ่งเป็นคนละ
ปัญหากับคนที่ยังไม่เห็นเลย — ตัวเลขรวมตัวเดียวจะกลบความต่างนี้

## ขอบเขตที่ยังไม่ทำในเช็คพอยต์นี้ — ระบุตรง ๆ

SoT §23 (Compliance Evidence) กำหนดให้รวมหลักฐานจริงจาก 13 หัวข้อ พร้อมสถานะ
`PASS/PARTIAL/FAIL/NO_EVIDENCE/N/A` และ **ห้าม claim PASS โดยไม่มี evidence จริง**

**ผมยังไม่ทำหัวข้อนี้ในรอบนี้** เพราะหลักฐานส่วนใหญ่ที่ §23 ต้องการ —
backup/restore test, DR drill, security scan, UAT, accessibility audit,
performance test — **เป็นผลของ INT-20 ที่ยังไม่ได้ทำ** · การสร้างหน้าจอ
Compliance Evidence ตอนนี้จะได้ตารางที่มีแต่ `NO_EVIDENCE` เกือบทุกช่อง
ซึ่งไม่ได้ช่วยใครและเสี่ยงที่จะมีคนกรอก PASS ลงไปเองโดยไม่มีหลักฐาน

**แผน:** ทำที่ **INT-20** หลังมีหลักฐานจริงจากงานความปลอดภัยและสมรรถนะ
แล้วจึงประกอบเป็นทะเบียนหลักฐานที่ทุกช่องชี้ไปยังผลรันจริงได้ (RISK-52)

ส่วนงานค้นหา (§25 "Search metadata ครบ") ทำแล้วผ่านรายงานทะเบียนที่กรองได้
ตามทิศทาง หมวด สถานะ และช่วงวันที่ · ตัวกรองระดับละเอียดกว่านี้รอ RISK-47
(มุมมองที่บันทึกไว้) ซึ่งมี API แล้ว
