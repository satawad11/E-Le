# การเฝ้าระวังจากภายนอกระบบ (RISK-54)

**อ้างอิง:** `SARABAN-V1.2-EXISTING-SYSTEM-MODULE-MASTER.md` §20, §27
**ฉบับ:** INT-22 · 2026-09-05

---

## ปัญหาที่เอกสารนี้แก้

ระบบมีกลไกเฝ้าระวังตัวเองครบแล้ว — ชีพจรของงานตามเวลา (INT-17) คิวข้อผิดพลาด
(INT-17) และการยกงานที่เงียบขึ้นมาเป็นรายการวิกฤต (INT-20)

**แต่ทั้งหมดนั้นเป็นงานตามเวลาเอง**

> ถ้า `schedule:run` ตายทั้งหมด ตัวเฝ้าระวังก็ตายไปด้วย และไม่มีอะไรบอกใครเลย

การเฝ้าระวังชั้นสุดท้ายจึง **ต้องมาจากนอกระบบ** — เป็นสิ่งที่โค้ดในโครงการนี้
ทำแทนไม่ได้โดยหลักการ ไม่ใช่เพราะยังไม่ได้ทำ

---

## จุดที่ต้องเฝ้า

| จุด | ต้องยืนยันตัวตนไหม | คืนอะไร |
|---|---|---|
| `GET /api/health` | **ไม่ต้อง** | `{"status":"ok\|degraded\|down"}` · HTTP **503 เมื่อ down** |
| `GET /api/ping` | ไม่ต้อง | `{"message":"pong"}` — บอกแค่ว่า PHP ตอบ |

**ให้ monitor เฝ้า `/api/health` ไม่ใช่ `/api/ping`**

`/api/ping` ตอบ 200 แม้ฐานข้อมูลล่ม พื้นที่จัดเก็บเขียนไม่ได้ หรืองานตามเวลา
ตายไปสามวัน — มันบอกแค่ว่าเว็บเซิร์ฟเวอร์ยังหายใจ

`/api/health` ตรวจ 8 ด้านจริง: ฐานข้อมูล · cache · คิว · พื้นที่จัดเก็บ ·
ตัวเรนเดอร์ PDF · ช่องทางส่งข้อความ · **งานตามเวลา** · ข้อผิดพลาดที่ค้าง

**ไม่เปิดเผยรายละเอียดภายในเลย** — คืนคีย์เดียว จึงเปิดให้ monitor ภายนอก
เรียกได้อย่างปลอดภัย · รายละเอียดอยู่หลังด่านสิทธิ์ที่
`GET /api/saraban/operations/health`

## ความหมายของแต่ละสถานะ

| สถานะ | HTTP | หมายความว่า | ควรทำอย่างไร |
|---|---|---|---|
| `ok` | 200 | ทุกด้านปกติ | — |
| `degraded` | 200 | ใช้งานได้ แต่มีบางอย่างผิดปกติ เช่น ฟอนต์ไทยยังไม่ติดตั้ง หรือมีข้อความส่งไม่สำเร็จค้างอยู่ | แจ้งเตือนแบบไม่ปลุกคนกลางดึก · เปิด `/saraban/operations` ดูรายละเอียด |
| `down` | **503** | มีด้านที่ใช้งานไม่ได้จริง เช่น ฐานข้อมูลล่ม เขียนไฟล์ไม่ได้ หรือ **งานตามเวลาตาย** | **ปลุกคน** |

> **`degraded` ตอบ 200 โดยตั้งใจ** — ถ้าตอบ 503 ระบบที่ยังให้บริการได้จะถูก
> load balancer ถอดออกจากการใช้งาน ทำให้ปัญหาเล็กกลายเป็นการล่มทั้งระบบ

## ตัวอย่างการตั้งค่า

### Uptime Kuma

| ช่อง | ค่า |
|---|---|
| Monitor Type | HTTP(s) |
| URL | `https://<โดเมนของระบบ>/api/health` |
| Heartbeat Interval | `60` วินาที |
| Retries | `2` |
| Accepted Status Codes | `200-299` |

Kuma จะแจ้งเตือนเมื่อได้ 503 (down) หรือเรียกไม่ได้เลย

**เพิ่มอีกหนึ่ง monitor สำหรับ `degraded`** ด้วย Keyword type:

| ช่อง | ค่า |
|---|---|
| Monitor Type | HTTP(s) - Keyword |
| Keyword | `"status":"ok"` |
| Invert Keyword | ปิด |

ตัวนี้จะเตือนเมื่อสถานะไม่ใช่ `ok` — ตั้งช่องทางแจ้งเตือนที่ไม่ปลุกคน

### cron + curl (ไม่มีเครื่องมือเฉพาะ)

```bash
# /etc/cron.d/eleave-health — ตรวจทุก 5 นาที
*/5 * * * * root /usr/local/bin/eleave-health-check.sh
```

```bash
#!/bin/sh
# /usr/local/bin/eleave-health-check.sh
URL="https://<โดเมนของระบบ>/api/health"

body=$(curl -sS --max-time 10 -w '\n%{http_code}' "$URL" 2>&1) || {
    logger -t eleave-health -p daemon.crit "เรียก $URL ไม่ได้: $body"
    exit 1
}

code=$(printf '%s' "$body" | tail -n1)

if [ "$code" != "200" ]; then
    logger -t eleave-health -p daemon.crit "ระบบ E-Leave ใช้งานไม่ได้ (HTTP $code)"
    exit 1
fi

printf '%s' "$body" | head -n1 | grep -q '"status":"ok"' || \
    logger -t eleave-health -p daemon.warning "ระบบ E-Leave อยู่ในสถานะ degraded"
```

> ส่ง log ระดับ `crit` ต่อไปยังช่องทางที่ปลุกคนได้จริง — การเขียนลง syslog
> เฉย ๆ แล้วไม่มีใครอ่าน คือปัญหาเดียวกับที่ RISK-57 แก้ไป

## ตรวจว่า monitor ทำงานจริง — ก่อนเชื่อว่ามันเฝ้าอยู่

**monitor ที่ไม่เคยถูกทดสอบ คือ monitor ที่ไม่รู้ว่าใช้ได้ไหม**

ทำสองข้อนี้บน staging แล้วยืนยันว่า **ได้รับการแจ้งเตือนจริง**:

1. **ทดสอบ `down`** — หยุดฐานข้อมูลชั่วคราว
   ```bash
   docker compose stop db
   curl -i https://<โดเมน>/api/health    # ต้องได้ 503
   docker compose start db
   ```

2. **ทดสอบ `degraded`** — หยุด scheduler แล้วรอเกินสองเท่าของรอบที่ตั้งไว้
   ```bash
   docker compose stop scheduler
   # รอ ~30 นาที (งาน outbox ตั้งไว้ทุก 5 นาที · เกณฑ์คือสองเท่า)
   curl -s https://<โดเมน>/api/health    # ต้องได้ down เพราะงานตามเวลาตาย
   docker compose start scheduler
   ```

บันทึกผลทั้งสองข้อไว้เป็นหลักฐานของรายการตรวจรับข้อ **ก.8**

## สิ่งที่ยังต้องเฝ้าแยกต่างหาก

`/api/health` ตอบได้เฉพาะเมื่อ **แอปยังตอบอยู่** · สิ่งเหล่านี้ต้องมี monitor ของตัวเอง
ที่ระดับ infrastructure:

| เรื่อง | เฝ้าอย่างไร |
|---|---|
| เครื่อง/คอนเทนเนอร์ล่มทั้งหมด | monitor เรียก `/api/health` ไม่ได้เลย = ครอบคลุมแล้ว |
| พื้นที่ดิสก์ใกล้เต็ม | monitor ของระบบปฏิบัติการ — แอปตรวจได้เฉพาะว่าเขียนไฟล์ได้ไหม |
| ใบรับรอง TLS ใกล้หมดอายุ | monitor ของ TLS แยกต่างหาก |
| ไฟล์สำรองไม่ถูกคัดลอกออกนอกเครื่อง | ขึ้นกับปลายทางที่เลือกใช้ · ระบบเห็นแค่ปลายทางที่ตั้งไว้ |
