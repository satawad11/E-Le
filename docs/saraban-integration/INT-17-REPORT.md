### 1. ทำไมคิวข้อผิดพลาดไม่ใช่ audit log และไม่ใช่ error log

|  | ตอบคำถามอะไร | แก้ได้ไหม |
|---|---|---|
| audit log | "เกิดอะไรขึ้น" | ❌ อ่านอย่างเดียว |
| error log | "ระบบพูดอะไรกับตัวเอง" | สำหรับนักพัฒนา |
| **คิวนี้** | **"อะไรค้างอยู่ที่ยังไม่มีใครแก้"** | ✅ มีเจ้าของ มีสถานะ ปิดได้ |

ถ้าไม่มีตารางนี้ ข้อผิดพลาดจะกระจายอยู่ใน log ที่ไม่มีใครเปิดอ่าน **จนกว่าจะมีคนโทรมาถาม**

**สองกติกาที่สำคัญที่สุด**

1. **ปัญหาเดิมที่เกิดซ้ำเป็นแถวเดียวที่นับจำนวนขึ้น** (`dedupe_key`) —
   ระบบที่แจ้งเตือนซ้ำพันครั้งเท่ากับไม่แจ้งเตือน เพราะคนจะเลิกอ่าน
2. **ปัญหาที่ปิดไปแล้วกลับมาอีก = เปิดใหม่** ไม่ใช่เพิ่มจำนวนครั้งของเรื่องที่ปิดแล้ว
   เงียบ ๆ · ถ้ากลับมาอีก แปลว่าการแก้ครั้งก่อนไม่ได้ผล ซึ่งต้องมีคนรู้

### 2. RISK-40 ปิดแล้ว — จับ "งานที่ไม่ทำงาน" ได้

**นี่คือความผิดปกติชนิดที่จับยากที่สุด** — งานตามเวลาที่หยุดทำงานจะเงียบสนิท
ไม่มี error ไม่มี log ไม่มีอะไรเลย · outbox ของศูนย์แจ้งเตือน (INT-14) และของ
webhook (INT-15) พึ่งงานตามเวลาทั้งคู่ ความเงียบจึงแปลว่าข้อความค้างโดยไม่มีใครรู้

ทางเดียวที่จับได้คือ **ตรวจจับการไม่เกิดขึ้นของเหตุการณ์** — ให้แต่ละงานประทับเวลา
ไว้ทุกครั้งที่ถูกเรียก (แม้รอบนั้นไม่มีอะไรให้ทำ) แล้วเทียบว่าเงียบเกินสองเท่าของ
รอบที่คาดไว้หรือยัง · เผื่อไว้สองเท่าเพราะงานที่รันทุก 5 นาทีอาจช้าไปหนึ่งรอบ
เพราะเครื่องยุ่ง ซึ่งไม่ใช่ความผิดปกติที่ต้องปลุกคน

หน้าจอวางเรื่องนี้ **ไว้บนสุดของศูนย์เฝ้าระวัง** — ถ้าอยู่ท้ายหน้า มันจะไม่ถูกเห็น

### 3. RISK-41 ปิดแล้ว — dead-letter มีเจ้าของ ไม่ใช่แค่มี API

INT-14/15 บันทึก `dead_lettered_at` ไว้แล้ว แต่ยังไม่มีใครถูกมอบหมายให้ตามแก้ ·
คำสั่ง `operations:sweep-exceptions` (ทุก 15 นาที) ทำให้ **ของที่มีอยู่แล้วกลายเป็น
งานที่มีเจ้าของ โดยไม่ต้องแก้โค้ดที่บันทึกมันไว้** — REUSE ที่แท้จริง

**สั่งซ้ำไม่ปิดรายการให้เอง** — การสั่งซ้ำไม่ได้แปลว่าสำเร็จ ผู้ใช้ต้องกลับมาปิดเอง
เมื่อยืนยันแล้ว · ถ้ายังล้มอีก รายการจะถูกยกขึ้นมาใหม่และจำนวนครั้งเพิ่ม

### 4. Feature Flag ≠ Permission — ข้อบังคับที่พิสูจน์ด้วยเทสต์

|  | ตอบคำถามอะไร | ต่างกันตามคนไหม |
|---|---|---|
| สิทธิ์ | "คนนี้ทำสิ่งนี้ได้ไหม" | ✅ |
| **ธง** | **"ความสามารถนี้เปิดอยู่ไหม"** | ❌ เหมือนกันทั้งระบบ |

เทสต์ `turning a flag on grants no permission to anyone` **เปิดธงทุกตัว** แล้วยืนยันว่า
ผู้ใช้ที่ไม่มีสิทธิ์ยังเข้าไม่ได้ — และผู้ที่จัดการธงได้ก็ยังเข้าทะเบียนหนังสือไม่ได้
ถ้าไม่มีสิทธิ์นั้น

**ธงมีผลกับพฤติกรรมจริง ไม่ใช่ตารางที่ไม่มีใครอ่าน** — ต่อเข้ากับสามจุด:

| ธง | ผลจริงเมื่อปิด |
|---|---|
| `saraban.webhooks` | `WebhookDispatcher` คืน 0 ไม่สร้างแถวส่งใด ๆ |
| `saraban.distribution.all_authorized` | `RecipientResolver` ปฏิเสธเป้าหมายนั้น (ไม่ใช่แค่ซ่อนปุ่ม) |
| `notification.web_push` | `WebPushChannelAdapter` รายงานว่าไม่ได้ตั้งค่า ทั้งช่องทางหยุด |

**ธงที่ไม่รู้จักถือว่าปิด** — ค่าเริ่มต้นที่ปลอดภัยของชื่อที่พิมพ์ผิดต้องเป็นการไม่ทำงาน
