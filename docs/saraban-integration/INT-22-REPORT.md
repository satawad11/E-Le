### 1. RISK-55 ปิดแล้ว — CI ตรวจสิ่งที่ชุดทดสอบตรวจไม่ได้

เพิ่มสองขั้นตอนเข้า `.github/workflows/ci.yml`:

**(ก) ติดตั้ง ghostscript** — ถ้าไม่มี เทสต์การปกปิดข้อมูล 3 ข้อจะ `skip`
แทนที่จะยืนยันว่าปกปิดได้จริง · **เท่ากับ CI ผ่านโดยไม่ได้ตรวจสิ่งที่สำคัญที่สุด
ของ INT-18** — การ skip ที่มองไม่เห็นอันตรายกว่าการล้มเหลว

**(ข) พิสูจน์การออกเลขหนังสือภายใต้การแย่งกัน** — ชุดทดสอบปกติรันบน SQLite
ซึ่งไม่มี row-level lock จริง **จึงพิสูจน์เรื่องนี้ไม่ได้เลย** · ขั้นตอนใหม่เปิด
8 process จริงแย่งกันออกเลขบน MySQL 8 แล้วตรวจสามข้อพร้อมกัน

> **หมายเหตุที่ต้องระบุ:** ผมยังไม่ได้เห็น CI รันจริงบน GitHub Actions
> (ไม่มีสิทธิ์เข้าถึง) · สิ่งที่ยืนยันได้คือ **จำลองขั้นตอนเดียวกันบนฐานว่าง
> ที่เพิ่ง migrate แล้วผ่าน** ซึ่งเป็นเงื่อนไขเดียวกับที่ CI จะเจอ

### 2. แบบทดสอบ UAT — เอกสารบันทึกผล ไม่ใช่คู่มือ

`docs/saraban-integration/UAT-SCRIPT.md` — **41 ข้อ ใน 7 ส่วน** ทดสอบโดย
**ผู้ปฏิบัติงานจริง 4 บทบาท** ไม่ใช่ผู้พัฒนา

**สิ่งที่ทำให้แบบนี้ต่างจากรายการตรวจทั่วไป**

- **มีตัวเลือก "ทำไม่ได้" แยกจาก "ไม่ผ่าน"** — สองอย่างนี้ต่างกัน และการบังคับให้
  เลือกแค่ผ่าน/ไม่ผ่านทำให้คนเลือกผิดเพื่อให้จบ ๆ ไป
- **มีขั้นตอนเตรียมการ 3 ข้อขึ้นก่อน** — ถ้าผู้ดูแลไม่ทำ ผู้ทดสอบจะติดตั้งแต่ข้อแรก
  และเสียเวลาทั้งวันโดยไม่รู้สาเหตุ
- **ข้อที่สำคัญที่สุดเขียนให้เห็นชัด** เช่น ข้อ 5.4:
  *"เปิดสำเนาที่ปกปิดใน PDF reader แล้ว **ลากเลือกข้อความ** ตรงส่วนที่ปิดทับ —
  ต้องคัดลอกออกมาไม่ได้เลย"* · นี่คือข้อที่แยกการปกปิดจริงออกจากกล่องดำหลอก ๆ
  และเป็นสิ่งที่ผู้ทดสอบต้องลองด้วยมือ ไม่ใช่ดูด้วยตา
- **ข้อ 2.6 ให้สแกน QR ด้วยมือถือที่ไม่ได้ล็อกอิน** — ทดสอบเส้นทางที่ผู้ตรวจสอบ
  ภายนอกจะใช้จริง ไม่ใช่เส้นทางที่นักพัฒนาคุ้นเคย
- **ส่วนที่ 7 ทดสอบด้วยแป้นพิมพ์อย่างเดียวและตรวจว่าสถานะไม่พึ่งสี** —
  สิ่งที่การทดสอบด้วยเมาส์บนจอใหญ่ไม่มีวันเจอ

### 3. รายการตรวจรับ — แยก "ตัวปิดกั้น" ออกจาก "ควรทำ"

`docs/saraban-integration/PRODUCTION-ACCEPTANCE.md` — **28 ข้อใน 5 หมวด**
โดย **16 ข้อทำเครื่องหมาย 🔴 = ห้ามขึ้นระบบถ้ายังไม่ผ่าน**

ทุกข้อมี **วิธีพิสูจน์ที่ทำได้จริง** ไม่ใช่ข้อความลอย ๆ:

| แทนที่จะเขียนว่า | เขียนว่า |
|---|---|
| "ตรวจสอบว่าสำรองข้อมูลทำงาน" | `php artisan backup:run` จบด้วย "Backup completed" |
| "ตรวจสอบว่ามีผู้มีอำนาจลงนาม" | `/saraban/authority/holders?ability=saraban.signature.sign` มีชื่อครบ |
| "ตรวจสอบว่า scheduler ทำงาน" | `/saraban/operations/health` → `scheduler` เป็น ok ไม่ใช่ degraded |

**หมวด ฉ. — สิ่งที่ยังไม่มีในระบบ** เป็นส่วนที่ผมคิดว่าสำคัญที่สุดของเอกสารนี้:
ตารางที่บอกตรง ๆ ว่ามีอะไรที่ยังทำไม่ได้ พร้อมผลต่อผู้ใช้ · **ไม่ใช่ข้อบกพร่อง
แต่เป็นขอบเขต** — ผู้อนุมัติต้องรู้ว่ากำลังรับอะไรไป ไม่ใช่มารู้ทีหลัง

## EVIDENCE

- ตัวเลขทุกตัวในหัวข้อ REGRESSION มาจากการรันจริงในเซสชันนี้ ไม่มีตัวใดคัดลอกมา
