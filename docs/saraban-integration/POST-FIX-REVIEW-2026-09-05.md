## 1. TOCTOU ของการทำลายเอกสาร — และสิ่งที่พบเพิ่มระหว่างพิสูจน์

**ข้อบกพร่องที่ 1 (ตามรายงาน):** `dispose()` ตรวจการอายัด **นอก** transaction
แล้วจึงเปิด transaction ลบไฟล์ · การอายัดที่มาถึงระหว่างสองจุดนั้นไม่มีผล

**แก้:** ย้ายการตรวจทุกข้อเข้าไปข้างใน transaction หลัง `lockForUpdate()` แถวหนังสือ ·
`placeHold()` ล็อกแถวเดียวกัน ทั้งสองงานจึงเข้าคิวกันจริง

**ข้อบกพร่องที่ 2 — พบเพราะสร้างเครื่องมือพิสูจน์ ไม่ได้อยู่ในรายงานต้นทาง:**

หลังแก้ข้อแรกแล้ว การรัน `saraban:concurrency-check --disposal` บน MySQL จริง
**ยังพบสถานะขัดกัน 6 รายการ** · สาเหตุคือ **ลบไฟล์อยู่ข้างใน transaction** —
เมื่อ InnoDB ยกเลิกรายการเพราะ deadlock/lock timeout (ซึ่งเกิดจริงเมื่อสองงาน
แย่งล็อกกัน) ทะเบียนย้อนกลับได้ **แต่ไฟล์ที่ลบไปแล้วย้อนกลับไม่ได้**

> ผลคือ **ไฟล์หาย แต่ทะเบียนบอกว่ายังไม่ถูกทำลาย** — แย่กว่าปัญหาเดิมเสียอีก
> เพราะไม่มีแม้แต่ hash ของสิ่งที่หายไป

**แก้:** เขียนทะเบียนให้ commit สำเร็จก่อน แล้วจึงลบไฟล์ผ่าน `DB::afterCommit()` ·
ทะเบียนเป็นแหล่งความจริง — เขียนไม่สำเร็จ ไม่มีไฟล์ใดถูกแตะเลย

**การเปลี่ยนพฤติกรรมที่ตั้งใจ:** `placeHold()` ปฏิเสธการอายัดหนังสือที่ถูกทำลายแล้ว ·
แถวอายัดบนเอกสารที่ไม่มีไฟล์ ทำให้ผู้อ่านทะเบียนเข้าใจผิดว่ายังถูกคุ้มครองอยู่ ·
ผลพลอยได้คือสถานะของหนังสือหนึ่งฉบับไม่กำกวมอีก จึงตรวจผลการแย่งกันได้ชัดเจน

## 4. ชั้นความลับ — ตามระเบียบว่าด้วยการรักษาความลับของทางราชการ พ.ศ. 2544

ยืนยันแล้วว่า `DocumentPolicy` **ไม่มีคำว่า `confidentiality` แม้แต่ครั้งเดียว** —
หนังสือชั้นลับที่สุดเปิดได้ด้วยเกณฑ์เดียวกับหนังสือทั่วไปทุกประการ

SoT §18 ระบุ `confidentiality` ไว้ในรายการนโยบายที่ต้อง versioned/published/
rollback/audit **แต่ไม่ได้กำหนดเนื้อหาของกติกา** · เนื้อหาจึงมาจากระเบียบราชการ
โดยตรง และตัวกติกาเองอยู่ในศูนย์นโยบายที่แก้และย้อนกลับได้ ไม่ได้ฝังในโค้ด

### สิ่งที่นำมาจากระเบียบ

**สามชั้นเรียงลำดับ (ระเบียบฯ ข้อ 12)** — `normal` (ไม่ลับ) ไม่ใช่ชั้นความลับ
ตามระเบียบ แต่เป็นสภาพปกติของหนังสือทั่วไป จึงมีอันดับ 0

| ชั้น | อันดับ | สิทธิ์ที่ต้องได้รับอนุญาต (ค่าเริ่มต้น) |
|---|---|---|
| ไม่ลับ (`normal`) | 0 | — ใช้เกณฑ์ขอบเขตหน่วยงานเหมือนเดิม |
| **ลับ** (`confidential`) | 1 | `saraban.confidential.view` |
| **ลับมาก** (`secret`) | 2 | `saraban.secret.view` |
| **ลับที่สุด** (`top_secret`) | 3 | `saraban.top_secret.view` |
| ชั้นที่นโยบายไม่ได้อธิบาย | — | **ปฏิเสธ** (default deny) |

**ผู้ได้รับอนุญาตชั้นสูงกว่า เข้าถึงชั้นที่ต่ำกว่าได้ (ระเบียบฯ ข้อ 26)** —
ตัดสินด้วย *อันดับ* ไม่ใช่การจับคู่ชื่อชั้นกับสิทธิ์แบบตรงตัว · ถ้าตัดสินแบบตรงตัว
ผู้ได้รับอนุญาตชั้นลับที่สุดจะเปิดหนังสือชั้นลับธรรมดาไม่ได้ ซึ่งขัดกับการปฏิบัติจริง
และจะบังคับให้ต้องแจกสิทธิ์ทั้งสามข้อให้คนเดียวกันเสมอ

**หลักความจำเป็นต้องรู้ (need to know · ระเบียบฯ ข้อ 26)** — การได้รับอนุญาต
ชั้นความลับไม่ได้แปลว่าเข้าถึงหนังสือลับทุกฉบับในระบบ · ต้องอยู่ในขอบเขตหน่วยงาน
เป็นเจ้าของเรื่อง หรือเป็นผู้รับหนังสือฉบับนั้นด้วย — ข้อนี้บังคับโดย
`OrgScopeResolver` ที่ชั้นถัดไปซึ่งมีอยู่แล้ว **ชั้นความลับจึงเป็นด่านเพิ่ม ไม่ใช่ด่านแทน**

**ทะเบียนการเข้าถึงข้อมูลข่าวสารลับ (ระเบียบฯ หมวด 4)** — บันทึกว่าใครเข้าถึง
เอกสารลับเมื่อใด ลงห่วงโซ่ audit เดียวกับการกระทำอื่น จึงแก้ย้อนหลังไม่ได้ ·
บันทึกเฉพาะชั้นอันดับ 1 ขึ้นไป (เกณฑ์ปรับได้จากนโยบาย) และ **บันทึกหลังผ่าน
`authorize()` เท่านั้น** — ความพยายามที่ถูกปฏิเสธไม่ใช่การเข้าถึง ถ้าปนเข้าไปด้วย
ทะเบียนจะตอบคำถามว่า "ใครเคยอ่านเอกสารฉบับนี้บ้าง" ผิด ซึ่งเป็นคำถามหลักของระเบียบ

**เจ้าของเรื่องและผู้รับหนังสือเปิดของตนได้เสมอ** (`owner_and_recipient_bypass`) —
ตรงกับระเบียบที่ให้ผู้ได้รับมอบหมายให้ปฏิบัติงานนั้นเข้าถึงได้ · ถ้าปิดข้อนี้
การส่งหนังสือลับถึงใครสักคนจะกลายเป็นการส่งที่เขาเปิดไม่ได้ — เท่ากับส่งไม่ถึง ·
ปิดได้จากนโยบายเมื่อหน่วยงานต้องการให้ชั้นความลับชนะแม้กระทั่งการเป็นผู้รับ

### สิ่งที่ยังต้องให้เจ้าของระบบตัดสิน

ระเบียบกำหนด **ชั้นความลับ** และ **หลักการเข้าถึง** ไว้ชัด แต่ **ไม่ได้กำหนดว่า
ตำแหน่งใดในโรงเรียนได้รับอนุญาตชั้นใด** — เป็นอำนาจของหัวหน้าหน่วยงานตามระเบียบฯ
หมวด 2 · จึง **ยังไม่แจกสิทธิ์สามข้อนี้ให้บทบาทใดเลย**

> ผลตอนนี้: หนังสือชั้นลับเปิดได้เฉพาะ **เจ้าของเรื่อง ผู้รับหนังสือ และ Super Admin**
> ซึ่งเป็นสภาพที่ปลอดภัยที่สุดและไม่ทำให้งานปกติสะดุด เพราะหนังสือทั่วไปไม่ถูกแตะ

ตรึงด้วย **7 เทสต์** — ครอบคลุมลำดับชั้นทั้งสองทิศทาง ทะเบียนการเข้าถึง
การไม่บันทึกหนังสือทั่วไป การไม่บันทึกความพยายามที่ถูกปฏิเสธ ชั้นที่ไม่มีกติกา
และการแก้กติกาจากศูนย์นโยบายได้จริง

# รอบที่สาม — ตั้งค่าเริ่มต้นชั้นความลับ (2026-09-05)

**คำสั่ง:** ตั้งค่าเริ่มต้นให้ · และ **แม้เป็นหนังสือลับ ผู้ที่เกี่ยวข้องในเรื่องนั้นต้องเข้าถึงได้ด้วย**

## ผู้ได้รับอนุญาตเข้าถึงชั้นความลับตั้งต้น

ยึดตามลำดับบังคับบัญชาของสถานศึกษา · **แจกทีละหนึ่งชั้น ไม่แจกชั้นที่ต่ำกว่าซ้ำ**
เพราะผู้ได้รับอนุญาตชั้นสูงกว่าเข้าถึงชั้นต่ำกว่าได้อยู่แล้วโดยตัวนโยบายเอง
(ระเบียบฯ ข้อ 26) — การแจกซ้ำทำให้ถอนสิทธิ์ในอนาคตได้ไม่หมดและตรวจสอบยาก

| บทบาท | ชั้นที่ได้รับอนุญาต | เหตุผล |
|---|---|---|
| **ผู้อำนวยการ** | ลับที่สุด | หัวหน้าสถานศึกษา · ผู้รับผิดชอบสูงสุดของหน่วยงาน |
| **รองผู้อำนวยการ** | ลับมาก | ผู้ปฏิบัติราชการแทนในสายงานที่รับผิดชอบ |
| **หัวหน้าบุคลากร** | ลับ | เรื่องบุคคล วินัย และการประเมิน เป็นชั้นลับตามปกติ |
| **เจ้าหน้าที่ธุรการ** | ลับ | ต้องลงทะเบียนและเดินเรื่องหนังสือลับที่เข้ามาในระบบ |
| ข้าราชการทั่วไป | — | เข้าถึงเฉพาะเรื่องที่ตนเกี่ยวข้อง ตามหลักความจำเป็นต้องรู้ |

ยืนยันบน dev แล้วหลัง `migrate`:

```
Director           => saraban.top_secret.view
Deputy Director    => saraban.secret.view
HR Head            => saraban.confidential.view
Document Officer   => saraban.confidential.view
Employee           => —
```

> **ระเบียบไม่ได้กำหนดว่าตำแหน่งใดได้รับอนุญาตชั้นใด** — เป็นอำนาจของหัวหน้า
> หน่วยงานตามหมวด 2 · ค่าเหล่านี้เป็นจุดตั้งต้นที่ผู้อำนวยการแก้ได้ทุกเมื่อจาก
> หน้าจอจัดการสิทธิ์ ไม่ใช่กติกาที่ระบบบังคับ

## "ผู้ที่เกี่ยวข้องในเรื่องนั้นก็เข้าถึงได้ด้วย"

ข้อนี้คือ **หัวใจของหลักความจำเป็นต้องรู้** และเดิมยังไม่ครบ — ระบบยกเว้นให้เฉพาะ
**เจ้าของเรื่อง** กับ **ผู้รับหนังสือเวียน** แต่ยังไม่ครอบคลุม **ผู้ที่เรื่องเดินมาถึง
ตามสายงาน** ซึ่งเป็นกลุ่มใหญ่ที่สุดของคำว่า "ผู้เกี่ยวข้อง"

เพิ่ม `isWorkflowParticipant()` เข้า `DocumentPolicy` นับสามกลุ่มจากสายงานเดินหนังสือ
ของฉบับนั้น:

1. **ผู้เริ่มเรื่อง** (`workflow_instances.initiated_by`)
2. **ผู้ที่มีงานในสายงานนี้** — ทั้งที่ค้างอยู่และที่ทำไปแล้ว
   (`assignee_user_id` · `completed_by` · `effective_actor_id`)
3. **ผู้ที่เคยลงมือทำอะไรกับเรื่องนี้** (`workflow_actions.actor_id` · `effective_actor_id`)

รวม **ผู้ปฏิบัติแทนตามการมอบอำนาจ** ด้วย เพราะนับ `effective_actor_id` ทั้งสองที่ —
ผู้รักษาการที่พิจารณาเรื่องแทน ย่อมต้องเปิดเรื่องนั้นได้

**ผลที่สำคัญ:** ผู้เกี่ยวข้องเข้าถึงได้ **แม้อยู่นอกขอบเขตหน่วยงาน และแม้ไม่ได้รับ
อนุญาตชั้นความลับนั้นไว้ล่วงหน้า** · ถ้าไม่มีข้อนี้ หนังสือลับที่เดินมาถึงโต๊ะใคร
ตามสายงานจะกลายเป็นหนังสือที่เขาเปิดไม่ได้ทั้งที่ต้องเป็นผู้พิจารณา — งานค้างทันที
และผู้ดูแลจะถูกบีบให้แจกสิทธิ์ชั้นความลับกว้างเกินจำเป็นแทน

ปิดได้จากนโยบาย (`workflow_participant_bypass`) เมื่อหน่วยงานต้องการให้ชั้นความลับ
ชนะแม้กระทั่งการอยู่ในสายงาน

### สรุปว่าใครเปิดหนังสือลับได้บ้าง

| ผู้เข้าถึง | ต้องได้รับอนุญาตชั้นความลับไหม | ต้องอยู่ในขอบเขตหน่วยงานไหม |
|---|---|---|
| เจ้าของเรื่อง | ไม่ต้อง | ไม่ต้อง |
| ผู้รับหนังสือเวียน | ไม่ต้อง | ไม่ต้อง |
| **ผู้อยู่ในสายงานเดินเรื่อง** | **ไม่ต้อง** | **ไม่ต้อง** |
| ผู้ค้นทะเบียนหนังสือของหน่วยงาน | **ต้อง** | **ต้อง** |

แถวสุดท้ายคือเหตุผลเดียวที่ต้องมีสิทธิ์ชั้นความลับเลย — มันตอบคำถามว่า
"ค้นเจอหนังสือลับของหน่วยงานได้ไหม" ไม่ใช่ "ทำงานในเรื่องที่ได้รับมอบหมายได้ไหม"

# รอบที่สี่ — ข้อค้างจากรายงานแก้ไขโมดูลลา (2026-09-05)

**ต้นทาง:** `docs/checkpoints/LEAVE-MODULE-FIX-2026-09-05.md` หัวข้อ "ข้อจำกัดและงานนอกขอบเขต"
ซึ่งระบุความล้มเหลว 2 รายการนอกโมดูลลา และบอกตรง ๆ ว่า **ไม่อ้างว่า full quality gate ผ่าน**

## ตรวจแล้ว — ทั้งสองข้อปิดไปแล้วในโค้ดปัจจุบัน

| ข้อค้าง | สถานะที่ตรวจพบจริง |
|---|---|
| `ApiSurfaceContractTest` — endpoint สารบรรณ/notification/operations ที่หน้าเว็บไม่มีใครเรียก | ✅ ผ่าน · เทสต์ถูกปรับให้เข้าใจ alias `api/v1/saraban/*` และ URL ที่ประกอบจาก composable |
| `RuntimeSecurityConfigurationTest` — `minishlink/web-push` เป็น `^11.0` | ✅ ผ่าน · `composer.json` ระบุ `11.0.0` ตายตัวแล้ว |

**ตรวจว่าไม่ได้ผ่านเพราะผ่อนเทสต์** — การเปลี่ยนแปลงที่ทำให้ `ApiSurfaceContractTest`
ผ่าน **เข้มขึ้น ไม่ได้อ่อนลง**: ข้อยกเว้นสามรายการที่เพิ่มเข้ามาระบุชื่อเทสต์ที่
ครอบคลุมแทนไว้ทุกข้อ และ `frontendUri()` ที่เพิ่มเข้ามาไม่ได้ยอมรับ alias เฉย ๆ
แต่ **ยืนยันว่า alias ชี้ไป action เดียวกัน มี HTTP method เท่ากัน มี middleware
ความปลอดภัยครบเท่าเดิม และมี `idempotent` เพิ่ม** ก่อนจะยอมนับ

## แต่พบสาเหตุที่ปัญหาทั้งสองซ่อนตัวได้ — และแก้แล้ว

ทั้งสองข้อถูกพบครั้งแรกตอนมีคนรันด้วย container ชั่วคราวที่ mount ทั้ง repo เอง
เพราะบนเครื่องพัฒนา **เทสต์แปดข้อที่ตรวจสัญญาข้ามฝั่ง `skip` ทุกครั้ง** —
container ของ backend mount แค่ `backend/` ไฟล์ระดับ repo จึงเข้าถึงไม่ได้

เทสต์ที่ข้ามคือชุดที่ตรวจเรื่องซึ่งไม่มีใครอื่นตรวจ:

- API ที่ไม่มีหน้าจอไหนเรียก (สัญญาระหว่างสองฝั่ง)
- เวอร์ชัน dependency ที่ยัง pin ไม่ตายตัว
- compose ของ production ที่เผลอเปิด Vite dev server
- เมนูที่ชี้ไปหน้าที่ไม่มีอยู่จริง และหน้าที่ไม่มีเมนูชี้ถึง

> **ด่านที่มีอยู่แล้วแต่ไม่เคยทำงาน คือด่านที่ไม่มี**

**แก้:** เพิ่ม mount แบบอ่านอย่างเดียวของ `frontend/` `.github/` และไฟล์ compose
เข้า `docker-compose.dev.yml` · อยู่ในไฟล์ dev **โดยเจตนา** เพราะ production
ไม่ควรมี source ของหน้าเว็บและไฟล์ CI อยู่ใน container ของ backend

```bash
docker compose -f docker-compose.yml -f docker-compose.dev.yml up -d
docker compose exec backend php artisan test
```
