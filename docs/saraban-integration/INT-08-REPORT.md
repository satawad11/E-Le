### หัวใจของเช็คพอยต์นี้ — ทำไมต้องมี `AuthorityResolver`

`WorkflowEngine::permissionCandidates()` ของระบบเดิมคืน **ทุกคนในระบบที่ถือสิทธิ์นั้น**
ซึ่งกว้างเกินไปสำหรับงานสารบรรณ — เจ้าหน้าที่สารบรรณของฝ่าย ก. จะกลายเป็นผู้มีสิทธิ์
ตรวจหนังสือของฝ่าย ข. เพียงเพราะถือสิทธิ์ชื่อเดียวกัน

`SarabanAssigneeResolver` จึงหรี่ให้เหลือเฉพาะผู้ที่ **มีอำนาจกับหน่วยงานเจ้าของหนังสือฉบับนั้น**
โดยถาม `AuthorityResolver` ซึ่งเป็น **projection ล้วน** จากข้อมูลของระบบกลางสี่แหล่ง:

| แหล่ง | ตอบอะไร |
|---|---|
| `permissions` (ผ่าน `PermissionEvaluator`) | ใครถือความสามารถนั้น (รู้จัก explicit deny + ชื่อที่เทียบเท่า) |
| `org_unit_managers` | ใครเป็นหัวหน้า/ผู้รักษาการหน่วยงานใด ณ วันใด |
| `permission_scopes` (ผ่าน `OrgScopeResolver`) | ขอบเขตที่ผู้ดูแลกำหนดรายบุคคล |
| `workflow_delegations` | ใครทำแทนใครอยู่ |

**ไม่มีตารางอำนาจของสารบรรณเลย** — มีเทสต์ยืนยันว่าไม่มีตารางชื่อ `*authorit*` ในฐานข้อมูล
ถ้าเก็บผลลัพธ์ไว้เป็นตาราง จะกลายเป็นข้อมูลคู่ขนานที่ล้าสมัยทันทีที่มีการย้ายหน่วยงาน
หรือมอบอำนาจ แล้วตอบคำถามเรื่องอำนาจผิดโดยไม่มีใครรู้

### เลขหนังสือออกตอนลงนาม ไม่ใช่ตอนสร้าง

ตามระเบียบงานสารบรรณ เลขที่หนังสือเป็นของหนังสือที่ผ่านการลงนามแล้ว การออกเลขให้
ฉบับร่างที่อาจไม่ได้ลงนาม จะทำให้ทะเบียนมีเลขที่ไม่มีหนังสือจริงรองรับ

**ถ้ายังไม่ได้ตั้งค่าชุดเลขของประเภทนั้น การลงนามจะล้มพร้อมข้อความบอกเหตุ (422)**
ไม่ใช่ลงนามผ่านไปเงียบ ๆ โดยไม่มีเลข — หนังสือที่ลงนามแล้วแต่ไม่มีเลขที่ ใช้เป็น
หนังสือราชการไม่ได้ และจะกลายเป็นงานค้างที่ไม่มีใครรู้ว่าค้าง

### RISK-20 ปิดแล้ว — สองชั้น

1. `options` คืนเฉพาะหน่วยงานที่ผู้ใช้มีอำนาจทำเรื่องแทน
2. **`store` ตรวจซ้ำที่ server** — กรองรายการในฟอร์มอย่างเดียวไม่พอ เพราะหน้าเว็บ
   ไม่ใช่ด่านความปลอดภัย (SoT §6) ส่ง id หน่วยงานอื่นเข้ามาตรง ๆ ต้องถูกปฏิเสธ
